# Decisions

**Goal:** know why BarrierKit is built this way before you change it.
**Reader:** anyone who changes the kit's structure, render stack, look or public names.

Each entry gives the decision as it holds today, with its ADR number. When a
decision changes, edit its entry; when it no longer holds, delete it. Git keeps
the history. The compositor, session and shell decisions are in
[Malaysia's decisions](https://github.com/HBlanqueto/malaysia/blob/main/docs/decisions.md).

## 0011 — Design values as Rust constants
Decision: every design value is a public compile-time constant of `ctdesign`, and no other crate defines one. A color that changes with window focus is a `FocusPair`.
Why: each value has one typed source; a missing token fails the build instead of hiding as a literal.
Code: `crates/ctdesign/build.rs`, `crates/ctdesign/src/lib.rs`, `scripts/check-design-tokens.sh`

## 0032 · 0046 — Tengen as the design source
Decision:
- The visual language is Tengen. Its source is `crates/ctdesign/tengen/tokens.json` and `components.json`.
- They hold colors, radii, spacing, typography, shadows and component metrics.
- `ctdesign/build.rs` generates `$OUT_DIR/tengen.rs` from them.
- The themes are `light` (default), `dark` and `dark-tint`.
- The kit draws the look itself; no alias keeps an old name or path.
Why: the kit, the shell and the compositor read the same values from one place.
Code: `crates/ctdesign/tengen/`, `crates/ctdesign/build.rs`, [Tengen](architecture/tengen.md)

## 0033 · 0034 · 0056 — Render stack
Decision:
- `bk` uses Freya's core crates pinned `=0.5.3`: `freya-core`, `freya-components` (no default features), `freya-edit`, `freya-animation`, `freya-engine`, `freya-clipboard`, `torin`, `ragnarok`.
- Never `freya`, `freya-winit` or any `otto-*` crate.
- Its own Wayland runner on smithay-client-toolkit and `calloop`.
- Skia runs only in clients. `ctdesign`, `ctappearance` and `infinity-protocol` pull no Freya or Skia, so the compositor never links them.
- The runner draws with Vulkan through `ash`, with no GL fallback. `freya-engine` builds Skia with only `vulkan`.
- One shared device and `DirectContext`, one swapchain per surface, `MAILBOX` when offered, else `FIFO`.
Why: winit would own the Wayland connection, and Freya's Vulkan driver lives in `freya-winit`. Frame callbacks already pace redraws, so `FIFO` would throttle twice.
Rejected: a kit from `otto-kit`; Skia on EGL/GLES.
Code: `crates/bk/src/platform/vulkan.rs`, `scripts/check-client-only-deps.sh`, [Platform](barrierkit/18-platform.md)

## 0035 — Own app identification and CSD
Decision: a window's `app_id` is `ctdesign::NATIVE_APP_ID_PREFIX` plus the app name, unless `WindowOptions::app_id` sets another. Every window requests client-side decoration; if the compositor answers server-side, the kit turns off its edge resizing.
Why: the prefix lets the compositor tell kit windows from the rest and leave their chrome to the kit.
Code: `crates/bk/src/platform/window.rs`

## 0039 — Infinity v1
Decision: `infinity_window_manager_v1` is a private Wayland protocol for the shell's window management. `infinity-protocol` generates the client side (feature `client`, used by `bk`) and the server side (feature `server`, used by the compositor). `bk` binds it only with the `shell` feature; the compositor decides which clients may bind it.
Why: the standard protocols do not cover what the Dock and the menu bar need from the compositor.
Code: `crates/infinity-protocol/protocols/`, `crates/bk/src/shell/infinity.rs`, [Wayland protocols](barrierkit/18-platform.md#wayland-protocols)

## 0041 · 0057 · 0065 · 0078 · 0079 — Sidebar: flat, backdrop and glass
Decision:
- The sidebar is flat and full height, as in macOS 27: no inset, rounded corner, rim or edge line; only its colour sets it apart from the content. Its geometry lives in `components.window.sidebar`; an app changes it through `SidebarStyle`. The floating island of ADR 0041 was dropped on 2026-11-20 (ADR 0079): macOS 27 does not draw it, and the user's `sidebar_style` key went with it. A file that still has the key loads; the key is ignored.
- A window with a sidebar draws the unified 52 title bar (`Bar::Unified`), with the traffic lights at (19, 19) inside the sidebar.
- Over a `Backdrop` the sidebar is transparent and sends no glass panel.
- Otherwise the sidebar is a glass panel: the kit leaves a hole and sends `set_glass` (Infinity window style, version 6) with the rectangle, corner, `base`, `solid` and `chroma`. There is no public API.
- The compositor fills the panel with `base` plus the blurred wallpaper's chroma and draws the rim; unfocused, it shows flat `solid`. Towards the edge that touches the content, `base` veils the fill, so the wallpaper's colours fade but stay.
- With no such compositor, or with reduce transparency or contrast, the kit paints the opaque sidebar itself.
- In full screen with a glass bar, the glass covers the whole top strip, not one column.
Why: only the compositor sees the wallpaper. The macOS sidebar keeps the app's lightness and takes only part of the wallpaper's chroma. The island was measured against macOS 27 (`docs/research/macos-control-metrics.md`, "Sidebar and window (macOS 27)") and does not exist there.
Rejected: a translucent fill over a plain blur region; it lets the wallpaper's lightness through and cannot say a corner. Keeping the island as a user option: nothing in macOS 27 backs it.
Code: `crates/bk/src/sidebar.rs`, `crates/bk/src/glass_panel.rs`, [Sidebar](barrierkit/10-sidebar.md)

## 0047 — BarrierKit in layers
Decision: `bk` is one crate in four layers (platform, primitives, views, patterns) plus a cross-cutting `app`. A layer uses only the layers below it, and patterns compose only the public API of views. Code only `malaysia-shell` uses lives in `src/shell/`, behind the `shell` feature.
Why: the kit must build any desktop app, like AppKit or libadwaita, without each app rebuilding sidebars, search fields and controls.
Pending: nothing is built until an app needs it. Partial damage waits for Freya: 0.5.3 repaints the whole tree every frame.
Code: `crates/bk/src/lib.rs`, [Layers](barrierkit/03-layers.md)

## 0048 — BarrierKit in its own repository
Decision: `bk`, `ctdesign`, `ctappearance` and `infinity-protocol` live in `github.com/HBlanqueto/barrierkit`. malaysia pins all four by one git `rev` in `Cargo.toml` and takes barrierkit as a flake input, reusing its prebuilt Skia. `./dev.sh kit-local` in malaysia tests a local checkout before publishing.
Why: the toolkit carries its style and its reading of the appearance; keeping them in malaysia would make the two repos depend on each other.
Code: `flake.nix`

## 0082 — Traffic lights as macOS 27 draws them
Decision:
- A light is the 14 pt disc of macOS 27: a vertical gradient fill (four stops), a 0.5 pt ring (three stops, a vertical gradient too), a halo in the light appearances and a glyph while the pointer is over the group. A pressed light grows to 16 pt and brightens (`TRAFFIC_PRESS`).
- Every color is a token measured per appearance, light, dark and Increase Contrast (`themes.*.traffic-lights`, `traffic-lights-contrast`); none depends on the accent.
- `standard` is that look as it is. `accent` and `wallpaper` give each light a tone and `ctappearance::traffic::looks` recolors its measured look with it: alpha, and lightness and saturation relative to the light's base, stay; the hue is the tone's; the glyph stays at 3:1.
- On macOS the style is always `standard`, so `accent` and `wallpaper` are Linux-only. The one exception is the graphite accent, which grays the lights the way `accent` would tint them.
- Skia rasterizes each light once per look at the window's scale (`bk/src/traffic_raster.rs`), like the symbol tiles.
- `traffic_light_shape` is gone: macOS 27 has no square light, and the ring, the halo and the press are defined for a disc. A file that has the key still loads, and a write drops it.
Why: the lights are the most seen control of a window, and the measurement says what they are (`docs/research/macos-control-metrics.md`, "Traffic lights (macOS 27)").
Rejected: keeping a corner radius in the style, which would need its own ring and halo for no macOS look; blending the glyph with plus-darker like macOS, which Freya cannot do, so the glyph is its measured final color.
Code: `crates/ctappearance/src/traffic.rs`, `crates/bk/src/traffic.rs`, `crates/bk/src/traffic_raster.rs`, `crates/ctdesign/tengen/`

## 0061 · 0062 · 0063 — SwiftUI-shaped API
Decision:
- An app depends only on `bk` and writes `use bk::prelude::*;`.
- `Application::new(name).window(title, content).run()` opens a window with background and `Titlebar`; `run_window` stays for a bare window; an app that draws its own bar sets `HiddenTitleBar` or `Plain` (ADR 0115).
- The crates are `bk`, `ctdesign` and `ctappearance`; prose still says BarrierKit.
- Every public view is a type built with `Type::new(..)` that forwards Freya's traits. Modifiers are methods of `ViewModifiers` (`.help`, `.context_menu`, `.focus_ring`).
- Low-level primitives stay functions, like `text(..)`, `rect()` and `label()`.
- Names follow SwiftUI, then AppKit, then plain English; the glossary lists each one.
Why: the common case needs one import and one expression, and the code reads like its SwiftUI version.
Code: `crates/bk/src/prelude.rs`, `crates/bk/src/app/scene.rs`, [Glossary](barrierkit/20-glossary.md)

## 0064 — Styles and themes
Decision:
- Each control has a style struct (`SliderStyle`) that implements `ControlStyle`. Its `tengen()` builds the default from `ctdesign`.
- An override is a closure from the inherited style to a new one.
- Levels, later wins: Tengen, `Theme` (`Application::theme`, `WindowOptions::theme`), `.control_style` on a container, `.style` on the instance.
- Paint is a `ShapeStyle`; `Role`, `Accent` and `Backdrop` follow the system, `Color` does not.
- The user's accessibility settings apply last: reduce motion, reduce transparency and the focus ring.
Why: an app changes any visual property, or builds a whole theme, without copying Tengen's numbers.
Code: `crates/bk/src/styles/theme.rs`, `crates/bk/src/styles.rs`, `crates/bk/src/modifiers.rs`

## 0080 — Accent colors
Decision:
- The accents are the nine of System Settings: Multicolor and eight named ones (`ctdesign::ACCENTS`). Multicolor is no entry: with no `accent` the controls are blue and an app keeps its own accent.
- Each named accent holds the colors it decides in four looks, light, dark and Increase Contrast light and dark, as measured on macOS 27.2.1 with the accent set per process. Blue points to the theme tokens, so no value is written twice.
- The user's choice is `accent = "<name>"` in `appearance.domain`. `accent_color` stays for a color macOS has no name for, and one that equals the light `control` of a named accent reads as that accent. `wallpaper_accent` stays; a monochrome wallpaper falls back to graphite.
- A color without a name has only its `control`. The rest follows a rule fitted to the named accents (`ACCENT_RULE`): the text selection color is exact, the selection and focus colors are an OKLab shift within a few levels, the control fills are the `control`. Where the ink does not reach 4.5:1, the fill darkens (WCAG 2.2 §1.4.3); a named accent keeps macOS's value.
- Text selection draws `selected_text`, the accent over the window at 30%.
Why: macOS has per-appearance values for every accent and no custom one; a single color for light and dark, and blue pressed and disabled fills under any accent, were wrong. The rule covers what macOS gives no value for.
Rejected: one hex per accent for both appearances (the dark values of red, yellow, purple and graphite differ); deriving the named accents from their `control` (the best formula misses the selection color by up to 6 levels and the focus ring by 14, so each accent has its own).
Code: `crates/ctdesign/tengen/components.json` (`settings.accents`, `settings.accent-rule`), `crates/ctappearance/src/accent.rs`, `crates/ctappearance/src/resolve.rs`, [Accents](barrierkit/04-appearance-and-tokens.md#accents)

## 0081 — Icons: glyphs in the kit, icon files in the theme
Date: 2026-11-20
Decision:
- A glyph is a one-color symbol the kit draws inside a control, menu, toolbar, sidebar, list, form or state. It is a `Symbol`: SVG paths on a 16 grid in `currentColor`, named after its SwiftUI name, fitted to AppKit at 16 pt (20 px).
- An icon is a file with a freedesktop name that other apps, the shell and malaysia load by name: apps, places and folders, MIME types, devices, and the `-symbolic` actions and status. It lives in `malaysia-icon-theme`.
- Neither repository holds a file from Apple. The paths and the theme files are drawings made for the project; the ink boxes and masses they were fitted to stay out of the repository.
- The kit does not read the theme and the theme does not read the kit. A glyph moves to the theme only when the theme lacks its freedesktop name and its owner asks for it.
Why: the kit draws a glyph at any size, stroke and color from one path, which a file lookup by name and size cannot do. The theme already ships the macOS-style set the desktop's apps need: about 3,700 symbolic icons, 50 folders, 235 file types, 63 devices; every freedesktop name that matches a kit glyph was found in it (50 checked). Copying the glyphs would draw each twice and mix the kit's MIT with the theme's LGPL, CC BY-SA and GPL licenses.
Rejected: every glyph in the theme (the kit would load files at run time or embed GPL art, and lose the stroke and the state colors); every icon in the kit (Linux apps look icons up by name and the kit is not an icon theme); drawing the theme's symbols from the kit's paths (it would replace the MacTahoe copies, which is the theme's decision).
Code: `crates/bk/src/symbol.rs`, `crates/bk/tests/kit/appkit_icons.rs`, `scripts/appkit-compare.py` (`icons`), [Macos icons](research/macos-icons.md)

## 0083 — What the kit does not cover
Date: 2026-11-21
Decision:
- Out of scope, so the [SwiftUI API gap](research/swiftui-api-gap.md) counts them apart and no backlog row asks for them:
  - Core Data: `FetchRequest`, `FetchedResults`, `SectionedFetchRequest`, `SectionedFetchResults`. The app owns its data and hands `List` its rows.
  - Network: `bk` fetches no URL. `AsyncImage` shows files and bytes (`use_artwork`, `use_artwork_from`); `asyncImageURLSession` has no counterpart.
  - HDR: `allowedDynamicRange` (modifier and environment value), `Color.headroom`, `Color.exposureAdjust`, `Image.DynamicRange`. The kit draws in SDR.
- Not out of scope: `Shader`, `ShaderLibrary`, `colorEffect`, `layerEffect`, `distortionEffect` and `MeshGradient`. Skia runs them in the app ([Shader needs](research/shader-needs.md)); the Metal libraries SwiftUI loads do not port, so the kit takes SkSL.
- Not a decision: WidgetKit, control widgets, visionOS spaces and the other Apple-only API are `n/a` in the gap study. Linux has no such host or hardware.
Why: before this entry no decision excluded an API, so every absent item counted as work. The first two are frameworks beside the toolkit that an app already has a better source for (its database, its HTTP client). HDR needs `wp_color_manager_v1`, an HDR swapchain and compositor support; malaysia does not advertise the protocol. ADR 0047 says "not yet"; this entry says "not in the kit".
Rejected: excluding `Shader` and `MeshGradient` as graphics frameworks, since Skia draws both and a plan exists; listing the Apple-only API here, since the platform already rules it out.
Pending: the document model (`DocumentGroup`, `FileDocument` and 24 more types). The [coverage matrix](research/swiftui-appkit-coverage.md) puts document frameworks outside its scope and its backlog D.7 plans document scenes; decide before building scenes. HDR returns when malaysia advertises `wp_color_manager_v1`.
Code: [SwiftUI API gap](research/swiftui-api-gap.md), [Shader needs](research/shader-needs.md)

## 0084 — Labels: owned text or a view
Date: 2026-11-21
Decision:
- Visible text a control takes (label, title, placeholder, caption, item) is `impl Into<Cow<'static, str>>`. A literal or a `tr!` result stays borrowed; a `String` is owned and needs no leak. The few that take `impl Into<String>` today, such as `Button::new`, change too.
- Identifiers stay `&'static str`: menu ids, `app_id`, pane ids and `GlassContainer` item ids.
- A control that shows a label takes a closure that returns the view, through a builder named `label` (SwiftUI's `label:`), which replaces the drawn text. The string given to `new` stays the accessible name. The control runs the closure inside a `TextStyle` scope that holds its font and the ink of its current state, and sets the same font and ink as Freya's inherited text style: `Text`, `Label` and a Freya `label()` take them.
- Order: the text type first (done 2026-11-21); then `Label` (a title and a `Symbol`, done 2026-11-21: `Label::new(title, Symbol)` in `crates/bk/src/elements.rs`, which shadows Freya's `Label` in the prelude); then the `label` builder: done 2026-11-21 for `Button` (`Button::label(|| view)`), the other controls when an app needs it (ADR 0047).
Why: a list built at run time (networks, files, users) leaks every text: `i18n::intern` keeps each distinct one for the life of the process. SwiftUI takes text or any view. The text change is source compatible: literals, `tr!`, `String`, `.map(Type::new)` and `fn(&'static str)` pointers still compile (checked with `rustc` on 2026-11-21), so each control written in the old form only adds one more signature to change. A view built by the app cannot see the control that will draw it: `Text` and `Image` fix their font and color when they are built, so an eager view in a `bordered_prominent` button drew the label ink and 750 to 2300 channels differed from the drawn text (2026-11-21), while a Freya `label()` sets neither and inherits. A closure runs in the control's render, after its scope exists. Freya's `Callback` never compares equal (`freya-core-0.5.3/src/event_handler.rs`), so a button with a label re-renders with its parent and the closure cannot show a stale value. Freya cannot read a name out of a view (it overwrites the accessibility label in `create_node` and has no text runs), so the string stays the AT-SPI name.
Rejected: an eager view for `label`, for the reason above, and `NoArgCallback` for the closure, which compares always equal and would leave a stale label; `impl Into<String>`, which copies every literal each time a view is built; one `impl IntoElement` parameter for both, since Freya turns a `&str` into a `label` with `to_string()` (`freya-core-0.5.3/src/elements/label.rs:73`) and the control would lose its accessible name; keeping `intern` for runtime lists, which grows without bound.
Pending: the `label` builder on controls other than `Button`. `Button` proves it: a view label is pixel equal to the drawn label in light and dark, plain, prominent, disabled and pressed, and in an unfocused window, at text size 1.0 and 1.3 (`crates/bk/tests/kit/button_label.rs`, `crates/bk/src/platform/tests.rs`). `Button` scales its text and symbol with `Font::scaled(text_size)` when it draws them, as `Text` does, and keeps its height. Two limits: a bare `Image::system` keeps its own color, so a symbol goes in a `Label`; a Freya `label()` has no line height, so it is pixel equal to the drawn label at 1.0 but not at 1.3.
Done, text type (2026-11-21, ADR 0086): the columns of `Table::new`, `Slider::labels`, the swatch names of `ColorWell` and `RuleKind::Choice` take owned text. The `Option` parameters (`GroupBox::new`, `PaneGroup::new`, `Form::highlighted`) take `Option<Cow<'static, str>>`, so a caller writes `Some("x".into())`. A caller that passed a borrowed `&str` or `&String` to an old `impl Into<String>` parameter passes a `String` now. `i18n::intern` stays: ids built at run time (pane ids) still need `&'static str`, and malaysia calls it 37 times until its rev moves.
Code: `crates/bk/src/controls/button.rs`, `crates/bk/src/styles/theme.rs`, `crates/bk/src/menu/model.rs`, `crates/bk/src/i18n.rs`, [SwiftUI API gap](research/swiftui-api-gap.md)

## 0085 — No `Binding`, no action routing or app lifecycle callbacks
Date: 2026-11-21
Decision:
- The kit has no `Binding`. A text control takes `State<String>`; every other control takes its value and a callback, and keeps a private copy until the app passes a new value (`use_controlled`).
- An action reaches every handler of the window: `use_menu_action` registers a handler and `dispatch` calls them all. The kit adds no routing to the focused view, no close veto (`windowShouldClose`), no quit call (`applicationShouldTerminate`) and no open-URL event (`application(_:open:)`). A close request closes the window at once, except a sheet's; closing the last window ends the process.
- Both are non-goals until an app asks for them; for documents the close veto, the quit and the open-URL event are built since [ADR 0112](#0112--accessibility-modifiers-by-swiftui-name-reach-voiceover-a-file-dialog-is-a-sheet-of-its-window-a-document-asks-before-it-closes). [SwiftUI to the kit](barrierkit/16-swiftui-to-the-kit.md) tells the app author the same.
Why: Freya 0.5.3 has `Writable<T>` and `IntoWritable` (`freya-core-0.5.3/src/lifecycle/writable.rs`), but its `PartialEq` returns `true` for any two values (line 60), so a component that holds one cannot show the diff that its source changed. Neither malaysia (working tree of 2026-11-21) nor curseterm (`1375c72`) uses `Writable`, `IntoWritable` or `use_radio` (grep). A grep of both for a close veto, a quit call and an open-URL event finds none; the only hits are winit's `CloseRequested` and `infinity_force_quit` in malaysia's compositor, which are not kit apps. The three repositories have no issue that asks for any of them (`gh issue list`, 2026-11-21). AGENTS.md rule 2 forbids adding what nobody uses.
Rejected: controls taking `impl IntoWritable` beside value plus callback, and a `Binding` type of the kit's own; no app uses either.
Pending: the action routing and `quit` return when an app of the kit needs one; a `Binding` returns when two components must edit one value and a `State<T>` in a context cannot serve them.
Code: `crates/bk/src/controlled.rs`, `crates/bk/src/app/action.rs`, `crates/bk/src/platform/window.rs`, [Swift syntax in Rust](research/swift-syntax-in-rust.md)

## 0086 — Views in list rows and table cells
Date: 2026-11-21
Decision:
- `List::row(|index| view)` and `Table::cell(column, |row| view)` take a closure that returns the view. It replaces the text the row or the cell would draw, as `Button::label` replaces a button's text (ADR 0084). The strings of `List::new`, `List::section` and `Table::rows` stay: they give the row count and the accessible names. A column without `.cell` draws its string, so a table mixes text and views. A table of text only is untouched: same code, same pixels.
- Each view runs inside a `TextStyleScope` that holds the table font and the ink of the row (`label`, or `selected_label` for a selected row), so `Text` and `Label` take them. Checked on 2026-11-21: a `Text` row and a `Text` cell, with and without icons and sections, draw the same pixels as the drawn text in light and dark, selected and focused (`crates/bk/tests/kit/list_rows.rs`).
- The closure gets the row index. Selection stays by index and `on_select` reports indexes; in a sectioned list the index counts across the sections (D6 stays open: no `Identifiable`).
- The row keeps `TableStyle::row_height`. No `listRow*` modifier is added: no height, inset or separator start of a row that holds a view is measured, and the table keeps the values of text rows.
- A press on a view reaches the row, which selects it. A control wraps itself in a `rect()` whose `on_press` stops the press (recipe 23); the controls do not stop it, as no control of the kit stops a pointer press.
- Text owned in collections (ADR 0084, done): `Table::new` takes `impl IntoIterator<Item = impl Into<Cow<'static, str>>>`; `Slider::labels` and `ColorWell::new` take a slice, `&[S]` with `S: Clone + Into<Cow<'static, str>>`, and copy it; `RuleKind::Choice` holds `Vec<Cow<'static, str>>`. A borrowed literal stays free; a `String` is owned.
- What stops compiling (checked with `rustc` on 2026-11-21): `Table::new(label, vec![])`, `Vec::new()` or a `.collect()` straight into the argument, `Slider::labels(&[])` and `ColorWell::new(label, &[])` (the element type is no longer fixed: write `Vec::<&str>::new()` or name the type); `RuleKind::Choice(&["a", "b"])` (write `Choice(vec!["a".into(), "b".into()])`), a `const` that holds a non-empty `Choice`, and any copy of a `RuleKind` (it is `Clone`, not `Copy`; `operators` and `Rule::matches` take `&RuleKind`). Malaysia (`1a45e115`) compiles unchanged: `Slider::labels` at `malaysia-settings/src/desktop.rs:84,100,211,228` and `app.rs:365,521,568,621,674` pass `tr_list!`, a `&'static [&'static str]`; `ColorWell::new` at `app.rs:270` passes `&ACCENT_SWATCHES`; `Table::new` and `RuleKind` have no call. `swatch_name(&'static str) -> &'static str` is unchanged (`icons.rs:204`).
Why: a view-valued row needs the font and ink of the row, so it is a closure the table runs in its scope, as the button label is. It is lazy: `VirtualScrollView` builds only the visible rows and calls the closure for those (`freya-components-0.5.3/src/scrollviews/virtual_scrollview.rs`), so a list of thousands of rows builds a screenful. `Callback` never compares equal (`freya-core-0.5.3/src/event_handler.rs`), so a table with a view cell redraws with its parent and cannot show a stale row.
Rejected: `Vec<Element>` for rows or cells (eager; it cannot see the row's font and ink and builds every row of a long list); a kit `ForEach` type (in this kit `ForEach` is `.children(iter)` with `.key(id)`; a second meaning for lazy rows would mislead); rows that take the height of their content (Freya's `VirtualScrollView` takes a fixed size or a closure by index, never a measured one); `Identifiable` selection (D6, open); `Vec<Cow<'static, str>>` as the parameter of `Table::new`, `Slider::labels` and `ColorWell::new`, which breaks every call that passes a `Vec<&str>` or `&[&str]`.
Pending: confirmation by the owner of the names `row` and `cell` and of the closure taking the row index. The height, insets and separator of a row with a view, the look of a control in a cell and the `listRow*` modifiers (`listRowInsets`, `listRowSeparator`, `listRowBackground`) wait for a SwiftUI probe of such rows. Rows that take the height of their content, per-row heights (`ItemSize` by index) and `ForEach` inside a `List` wait for a request.
Code: `crates/bk/src/views/list.rs`, `crates/bk/src/views/table.rs`, `crates/bk/src/styles/theme.rs`, `crates/bk/tests/kit/list_rows.rs`, `agents/recipes/list_rows.rs`, [SwiftUI API gap](research/swiftui-api-gap.md)

## 0087 — Ambient `disabled`, environment values, focus by name and button shortcuts
Date: 2026-11-21
Decision:
- `.disabled(bool)` is a method of `EnvironmentModifiers` and takes any view. It wraps the view in a scope that provides `isEnabled` through a context and reads the one above it: a control is disabled when its own `.disabled` or any scope above it says so, and a scope with `false` enables nothing that an outer one disabled (as in SwiftUI). The scope is always in the tree, so turning it on and off keeps the state of what is inside. A control reads it with `use_disabled(own)`; an app reads it with `use_is_enabled()`.
- The 19 controls with a `disabled` method follow it and draw as their own flag draws them (pixel test `crates/bk/tests/kit/ambient.rs`, light and dark). `MenuButton`, `ComboButton`, `HelpLink`, `Link` and the items of `ToggleGroup` follow it too, but they only stop reacting (no press, no focus, no hover) and are announced as disabled: their disabled look is not measured, so they are not dimmed. `ControlGroup`, `ToolGroup` and `ProgressView` have nothing to disable: the buttons inside follow it, and a progress view is not interactive. Not followed yet: the rows of `List`, `Table`, `OutlineView` and `CollectionView`, tabs, sidebar items, the media controls, the indicators, `ImageWell`, `TokenField` and `TextEditor`.
- `.environment(value)` puts a value in the environment of a view, and `use_environment::<T>()` reads the nearest one, or `T::default()` when none is above. The type is the key, so an app wraps a `bool` or a `String` in its own type; `T` is `Clone + PartialEq + Default`. The scope keeps one `State<T>` and writes the new value in its render, so a reader that read it renders again when the value changes (`ambient.rs`). `use_environment` reads the context on every render and takes no hook slot, as `resolve` does for `State<Theme>`.
- Not reactive, or not reached: a value given to `use_provide_context`, which `use_hook` caches for the life of the view (`freya-core-0.5.3/src/lifecycle/context.rs:244,280`); popups, menus, tooltips and sheets, which are other Freya runners opened with an `AppComponent` of their own and carry only the theme (`platform/popup.rs:151`, read, not run); the `value` of `.focused`, which is read when the view mounts.
- `FocusState<T>` (`use_focus_state::<T>()`, `T: Clone + PartialEq`) names the focus targets of a window. `.focused(state, value)` registers the controls inside the view under `value`: each `use_interaction` and the text inputs (`TextField`, `SecureField`, `SearchField`, `TextEditor`, `ComboBox`, `TokenField`). `state.get()` is the value of the focused one, `state.set(Some(v))` moves the focus to the first control registered under `v`, `set(None)` takes it off, and `.default_focus(state, value)` focuses `value` once, after its view has appeared. `get` is derived from the window's focus and holds no copy, so after `set` it changes in the next pass.
- `Button::keyboard_shortcut(Shortcut)` calls the button's `on_press` on a key press that `Shortcut::matches`, only while the button is enabled. It listens to the window's global key event, so the matching stays in `app/action.rs`. A key that a menu item of the window carries goes to the menu and never reaches the button (`platform/linux/seat.rs`, `key_event`), and a shortcut without a modifier also fires while a text field has the focus. A menu `Action` already takes `.shortcut`.
Why: a form that is disabled while a task runs needed one `.disabled` call per control (17 controls had the method, 8 had none), an app could not put its own model in the environment of a subtree, and a shortcut or a focus move by name had no path outside a menu item or a raw `AccessibilityId` ([SwiftUI API gap](research/swiftui-api-gap.md), rows 10 to 12). The scope pattern is the one `StyleScope` uses for themes. A state written in the scope's render and read in the readers' is the only way Freya 0.5.3 makes a context change visible.
Rejected: making `use_provide_context` and `use_consume` reactive, since `use_hook` caches their value; a hook slot in `use_environment`, which made an existing test panic with a hook-order error once it ran in every control (`preferences_search_opens_the_result_chosen_with_the_arrows`, 2026-11-21); an `EnvironmentKey` trait with a default value, since `Default` says it and the type is the key; letting `.environment` re-enable what `.disabled(true)` disabled (SwiftUI allows it through `\.isEnabled`; nobody asks); a `use_shortcut` registry consulted by `Runtime::key_event` (the gap study's proposal), which edits `app/action.rs` and the platform when Freya already sends the key to every node that listens globally; an `a11y_id` builder on each control for focus; a `State<Option<T>>` synced both ways by effects, which has two writers racing for one value.
Pending: confirmation by the owner of the choices the kit made without one: `Default` as the default of an environment value; the list of views that follow `disabled`, and that five controls go inert without being dimmed until their look is measured; `FocusState::get` lagging one pass behind `set`; a button shortcut that the menu overrides. Not done: `Shortcut::DEFAULT_ACTION` and `CANCEL_ACTION` (the constants are in `app/action.rs`, which another change owns), the default-button look that `.keyboardShortcut(.defaultAction)` gives in SwiftUI, and `focusScope`, `focusedValue` and `isFocused`.

## 0088 — Scenes, open and dismiss window, and the standard menus
Date: 2026-11-21
Decision:
- An `Application` declares scenes. `.window(title, content)` is a `WindowGroup` with the id `MAIN_WINDOW`; `.scene(..)` takes a `WindowGroup`, a `Window` or a `Settings`; `.options(..)` changes the scene declared last; `.run()` opens the first scene that is not `Settings` (`RunError::NoWindow` if none). `app::Scene` is now what `.scene(..)` takes, as SwiftUI's `Scene` is; the old `Scene` (one window with `.options` and `.run`) is gone, and its two methods moved to `Application`. A chain that did `Application::new(..).window(..).options(..).run()` compiles unchanged.
- `use_open_window()` gives `open(id)` and `open_value(value)`; `use_dismiss_window()` gives `dismiss()` and `dismiss_id(id)`. A `Window` or `Settings` that is open is fronted, not opened twice. A `WindowGroup` opens a new window each time. A `WindowGroup::for_value::<T>` (`T: Clone + PartialEq`) fronts the window with an equal value. A value is not stored, so open windows are not restored.
- Windows open without `freya-winit` (ADR 0033), through the runner the kit already has: `WindowControls::open_window` sends `WindowCommand::Open`, which `process_window_commands` turns into `Runtime::create_window` (`platform/window.rs`), an `xdg_toplevel` made with smithay-client-toolkit; `UtilityWindow::open` reaches the same function through `KitSender` and `OpenUtility` (`platform/runtime.rs`, `insert_ping`); popups are `xdg_popup`s (`platform/popup.rs`). A scene adds no platform code to open a window.
- The list of open windows is the kit's own. Wayland gives a client no list of windows and no way to raise one. Each scene window adds its `WindowControls` to a `State<Vec<_>>` when it mounts and removes it with `use_drop`, which runs when the window's Freya `Runner` drops on close (`freya-core-0.5.3/src/runner.rs:193`). Fronting calls `make_key_and_order_front`, which asks for xdg-activation with the last input serial. Each scene window republishes the items of its own Window menu when the list changes (`MenuHandle::set_menu_items`). Titles are the ones the scene declared.
- `Commands` is on by default (ADR 0115): each scene window that has no `WindowOptions::menu` of its own gets the standard menus, and `.commands(..)` replaces them: the app name (Settings…, Quit), File (New Window, Close), Edit (Undo, Redo, Cut, Copy, Paste, Delete, Select All, and Find ▸ with `.text_editing()`), View (Enter Full Screen), your `CommandMenu`s, Window and Help. Titles, order and key equivalents are the ones a SwiftUI app builds, measured on macOS 27.2.1 in English and Spanish ([the measurement](research/macos-standard-menus.md)). `CommandGroup::before`, `after` and `replacing` take a `CommandGroupPlacement`, the 12 groups the kit fills. Shortcuts map ⌘ to Ctrl, ⌥ to Alt, ⇧ to Shift; Help is F1 because ⌘? depends on the layout.
- The kit serves `NEW_WINDOW`, `CLOSE_WINDOW`, `SETTINGS`, `QUIT`, `MINIMIZE`, `ZOOM`, `BRING_ALL_TO_FRONT` and the Window menu items. `QUIT` closes every window one by one, which ends the process by the rule of ADR 0085; it is a menu item, not a function an app calls. Undo, Redo, Cut, Copy, Paste and Select All go to a focused text field first (ADR 0115); otherwise the Edit, Find and Help items need a handler and start disabled until the app calls `use_menu_enabled`; Undo and Redo follow `use_undo`. A text field keeps its own Ctrl+X, C, V, A and does not touch the menu.
- A scene saves its own window size: `WindowOptions::scene` makes the key `<app_id>.window.<scene>`, and `MAIN_WINDOW` keeps `<app_id>.window`. Before this, windows opened with `open_window` took the size saved by the main window and overwrote it on close.
Why: one `Application` had one window; `open_window` returned nothing, had no id and no way to front, close or list a window; a second window shared the first one's saved size. The standard menus were built by hand in each app. `Application` already owns the first window and the runner already opens the rest, so the scene layer is a registry and two hooks on top of `WindowControls`, and the menus are data over `MenuItem`.
Rejected: the AppKit window list through `ext_foreign_toplevel_list_v1`, which lists other clients' windows and does not raise them; `Codable` values and a stored list of open windows, which need restoration that the kit lacks (`xdg_session_management_v1` is staging); Cut, Copy, Paste and Find enabled by default, since nothing would handle them; a `quit()` function, a close veto and routing to the focused view (ADR 0085); an `app::Scene` kept as "one window", which clashes with SwiftUI's `Scene`.
Pending: confirmation by the owner of the choices the kit made without one: `Application::window` as a `WindowGroup`, so New Window appears in a single-window app that installs `Commands`; `QUIT` as close all; F1 for Help; the items that start disabled. Malaysia's menu bar builds its own App, Window and Help menus and merges a menu of the app into them by title (`malaysia-shell/src/menubar/remote.rs`, `MenuSources::compose`): a menu titled like the app fills its slots by label, so Settings… and Quit are taken over; the items of a Window menu are appended to its own, so Minimize, Zoom and Bring All to Front appear twice until Malaysia merges them by label as it does for the app menu. Not built: About, Services, Hide, View, Format, the sidebar, toolbar and inspector commands, Close All (an alternate), `commandsRemoved`, `openSettings`, `SettingsLink`, `defaultLaunchBehavior`, a window position, and the document scenes of ADR 0083, which this layer does not decide.

## 0089 — Layout primitives: `Spacer`, `frame`, `Grid`
Date: 2026-11-21
Decision:
- `bk::layout` adds `Spacer`; `Frame`, which `view.frame()` returns; `Grid`, `GridRow` and `GridCell`, with the modifiers `grid_cell_columns` and `grid_column_alignment`; and `HorizontalAlignment`, `VerticalAlignment` and `ContentAlignment`. `ContentAlignment` is SwiftUI's `Alignment`: torin's `Alignment` already holds that name in the prelude.
- This is option (b) of decision D4 of the AppKit gap study: flex recipes plus `Grid`, `Spacer` and the alignments torin can state. There is no constraint solver and no second layout engine.
- `Spacer` is a custom element with no axis. When a kit container converts to an element (`forward_element!`), a `Spacer` among its children gets the container's direction, and a container that holds one gets `Content::flex()` if its content is the default and `Size::fill()` on its own axis if that size is `Inner`, as SwiftUI stretches a stack with a `Spacer`. A container with no `Spacer` is unchanged. The default `min_length` is `SPACE_2` (8): measured on macOS 27.2.1, `Spacer()` is 8 long in a fitting `HStack` and `VStack`, 0 across, and two spacers share the free space equally.
- `frame()` wraps the view in a `rect()` centered on both axes; `Frame::alignment` sets `main_align` and `cross_align`; the sizes are Freya's `width`, `height`, `min_width` and `max_width`. `frame(maxWidth: .infinity)` is `.width(Size::fill())` in a column and `Size::flex(1.0)` in a row of `Content::flex()`; torin gives `Fill` its size in every phase and `Flex` only in the last (`torin-0.5.3/src/values/size.rs`, `eval`).
- `Grid` is a custom element. The cells of each column go in a vertical stack, so torin sizes a column to its widest cell before any post-processing; the stacks sit in a horizontal flow `horizontal_spacing` apart; a cell that spans columns floats (absolute position) over them. `post_measure` (`freya-core-0.5.3/src/element.rs`, the hook that Freya's paragraph uses for inline children) reads every cell's size, gives each column its widest cell and each row its tallest, widens spanned columns, and moves each cell to its slot. The columns reach the Grid through the node data that torin keeps per node (`torin-0.5.3/src/custom_measurer.rs`), so no element shares state with another.
- Measured on macOS 27.2.1 and asserted in `crates/bk/tests/kit/layout.rs`: cells are centered in their slot by default; `Grid(alignment:)`, `GridRow(alignment:)` and `gridColumnAlignment` move them (a spanning cell ignores the column alignment); a span's extra width is split equally among its columns (columns 10 and 50, span 200: both grow by 68, cells at 34 and 116); a view outside a `GridRow` spans all columns and is centered; a short row takes the first columns; the horizontal gap is 8.
Why: no gap of the SwiftUI studies is hit more often by app authors than these (gap 3 of the SwiftUI study, gap 8 of the AppKit study), and Malaysia builds each of them by hand with `rect()`, `Size::flex` and measured widths. Torin 0.5.3 has no track sizing, so the columns of a `Grid` cannot be a property of one container: a flat grid of cells moved by `post_measure` is exact after layout, but torin places a Grid from the size it had before `post_measure`, and with flat cells that size was the widest cell, 34 px off in a centered stack (measured). Column stacks make the width exact before it.
Limits (not exact):
- The height torin sees before `post_measure` is the tallest column. A parent that aligns its children (center, end, space-between) places the Grid by it, so a Grid whose tallest cells of different rows are in different columns lands off: two rows of 30 px cells in different columns, in a 200 px centered stack, give a 60 px Grid at y=80 where SwiftUI centers it at y=70 (measured). A parent aligned `Start`, or a Grid with its own `height`, is exact. A spanning cell is not in the width before `post_measure` either.
- Cells are content-sized. A cell with `Size::fill()` or `Size::flex` takes the Grid's available width, not its column's, so SwiftUI's `Divider` that stretches to the Grid needs a width here.
- Both gaps default to `SPACE_2`. SwiftUI measured 8 between controls and 0 between lines of text vertically; the kit does not tell them apart.
- No `gridCellAnchor`, `gridCellUnsizedAxes` or hidden rows. `Leading` and `Trailing` are left and right (decision D2, right to left, is open).
- Baseline alignment (`HStack(alignment: .firstTextBaseline)`, `GridRow(alignment: .firstTextBaseline)`) is not built. Torin cannot state it: a measurer returns a size and a data value, and a paragraph returns `()` and keeps its baseline inside its element (`freya-core-0.5.3/src/elements/paragraph.rs`), so no layout node and no `post_measure` can read it. The kit could compute it from font metrics for a `Text`, but not for a button or a field, and SwiftUI aligns through those (measured: the first baseline of a padded text is the text's own); a partial version would be inexact. It needs a Freya change (decision on Freya: patch or fork).
Rejected: a constraint solver beside torin (D4a), which is the owner's call and an engine to maintain; a flat grid with one element and `post_measure` only, which is smaller but wrong in a centered parent; rows of cells with the widths passed through node data, which makes the height exact and the width not, and widths vary more than heights; `ViewThatFits` and a custom `Layout`, not asked for here.
Pending: confirmation by the owner of D4 option (b) (no solver), of the names `ContentAlignment` and `Frame`, and of `.frame()` followed by Freya's size methods in place of arguments; the choice of `Size::fill()` for a stack that holds a `Spacer`; and the baseline, which waits on how Freya is treated.
Code: `crates/bk/src/layout.rs`, `crates/bk/src/elements.rs`, `crates/bk/src/modifiers.rs`, `crates/bk/tests/kit/layout.rs`, `agents/recipes/layout_grid.rs`, [AppKit gap](research/appkit-gap.md), [SwiftUI API gap](research/swiftui-api-gap.md), [Layout](barrierkit/11-views.md#layout)

## 0090 — Symbols: the regular stroke, weights, scales and hierarchical mode
Date: 2026-11-21
Decision:
- `SYMBOL.stroke` is 1 grid unit, not 1.4. SwiftUI's `ImageRenderer` at 8x puts the regular stroke at medium scale at 1.19 to 1.40 pt by symbol (1.31 pt on average) at 16 pt, which is 1.05 units on the grid of 1.25 px per unit; the 56 symbols of 2026-11-20 are fitted at 1. `SYMBOL.fine_stroke` stays, equal to `stroke`, because malaysia reads it.
- `Image::font_weight(SymbolWeight)`, `Image::image_scale(ImageScale)` and `Image::symbol_rendering_mode(SymbolRenderingMode)` are SwiftUI's `.fontWeight`, `.imageScale` and `.symbolRenderingMode` for one symbol; the weight type is `SymbolWeight` (UIKit's name) because `FontWeight` is Freya's and the prelude would shadow it in every app. The nine weights and the three scales read three tables of `components.json` (`symbol.weight-stroke-{small,medium,large}`, as a multiple of the regular stroke per grid unit of the scaled box) and `symbol.scale-size` (0.793, 1, 1.275 of the box). They apply to `Image::system` only.
- Hierarchical mode draws the layers SF dims at `symbol.hierarchy` (1, 0.5, 0.25). `Symbol::dimmed` says which sub-paths of a symbol's path are dimmed and at which level: 30 of the 36 symbols SF dims (the screens of `desktopcomputer`, `display` and `tv`, the dots of `macwindow` and a 5 pt² layer of `printer` are not drawn). The other symbols draw the same in both modes.
- `ArrowDown` is `arrow.down`; the old `ArrowDown` (`arrow.down.to.line`) is `ArrowDownToLine`. 27 symbols are new (151 in all), fitted with the bench of 2026-11-20. A test renders every row of `ICONS` and fails if the 16 grid cuts its ink; it found four of the 56 symbols of 2026-11-20 cut, which moved inside.
- 2026-11-22: 36 of the 65 older symbols are redrawn to the same frame (`macos-icons.md` 3.3). `Checkmark`, `Star`, `StarFill`, `QuestionMark` and `Dot` (5 of the 65) are not: the checkbox mark, the menu check, the rating indicator, the help button and the date picker's mark stand in for art AppKit draws itself and were sized to them. `Forward`, `Backward`, `Battery`, `Pause` and `Play` are solid shapes, `Ellipsis` is filled and stroked; the symbols wider than the grid are fitted to 15.8 units wide. The weight type is `SymbolWeight`, not `FontWeight` (`bk::prelude` shadowed Freya's and broke malaysia's `FontWeight::BOLD`).
Why: the 1.4 came from before the frame of ADR 0081 and was never measured; it was 35% too heavy against SF. The AppKit raster of 2026-11-20 read the stroke at the small scale (1.25 pt), the vector render reads each scale and weight without pixel snapping. SF weights and scales are not a stroke multiplier alone: the scale changes the box and the stroke by different factors, so each scale has its own table.
Rejected: keeping 1.4 and fitting new symbols at 1 (two weights in one set); one multiplier per weight for all scales (up to 10% off at black weight and small scale); a `Symbol` per layer or per weight (the kit draws one path at any stroke); redrawing `Checkmark`, `Star`, `StarFill`, `QuestionMark` and `Dot` with the rest: drawn to the SF frame the checkbox mark went from 4.1% to 5.6% of pixels off AppKit's, the rating from 7.5% to 25.4% and the help button from 4.9% to 5.6% (`appkit-compare.py controls`, 2026-11-22).
Pending: confirmation by the owner that the controls' own symbols (those drawn with `symbol()` and `stroked_symbol()`) take the new stroke; the environment `.imageScale` and `.fontWeight` (ADR 0087 gives the kit an environment; the symbols a control draws do not read it); palette and multicolor modes; the controls that draw their own AppKit art with a `Symbol` (checkbox, menu check, rating, help, date picker mark), which would let those five be redrawn; the 24 other older symbols not redrawn (macos-icons.md section 3.3); removing `SYMBOL.fine_stroke` once malaysia stops reading it.

## 0091 — The compositor composes every blur
Date: 2026-11-21
Decision:
- Malaysia's compositor composes every blur, as macOS's render server does: behind a window, behind a layer surface and inside a BarrierKit window. An app declares a material and a style and draws no backdrop blur. This is the kit side of Malaysia's «Blur and wallpaper tinting», whose blur lines it replaces (Malaysia ADRs 0020 · 0038 · 0065 · 0071); the text for Malaysia's `decisions.md` is in [the design](research/blur-backdrop-design.md#83-malaysias-adr-ready-to-paste).
- `infinity_window_style_v1` version 10 adds `set_backdrop(surface, blending, material, radius, rects)` and `set_scroll_edge(surface, edge, style, depth)`. `material` lists the 14 `NSVisualEffectView.Material` values the macOS 27.2 SDK does not deprecate (`NSVisualEffectView.h`) and `glass_regular` and `glass_clear` (`NSGlassEffectView.Style`); `blending` is `behind_window` or `within_window`. The protocol carries no blur radius, saturation or tint: the compositor takes them from `ctdesign` per material and appearance, and the blur reaches the same distance in logical pixels at every output scale.
- `within_window` blurs what the surfaces of the toplevel draw below the requesting surface: its parent, the sub-surfaces under it and their children. The requester may be a sub-surface above its parent, below it, or the root with a sub-surface under it. It never reads the region of `ext-background-effect-v1`, so a request on the root surface does not meet Malaysia's wallpaper blur.
- On a synchronized sub-surface the request applies with the parent's commit, so material and content change in one frame. A desynchronized sub-surface tears (phase 0: 23 of 23 mid-frames).
- A capture of a window alone includes `within_window` material and not `behind_window` material, as `screencapture -l` does on macOS 27.2.1.
- `ext-background-effect-v1` stays for every client that is not BarrierKit. The compositor serves `set_backdrop` and `set_scroll_edge` only for BarrierKit clients.
- Existing requests keep their opcode and meaning. A client sends the new ones only when it bound version 10 or later: a request newer than the object's version is a protocol error (`wayland-backend` 0.3.17, `src/rs/server_impl/client.rs:580`), not an ignored message. The kit binds `1..=9` until it sends them, and Malaysia advertises 10 only when it serves them.
Why: macOS composes the blur outside the app in both blending modes and the app declares the material (`docs/research/blur-ownership.md` 1.2, measured on macOS 27.2.1). One place then decides the radius, the tint and Reduce Transparency, and one algorithm gives each material its measured extent. Phase 0 (software rendering, `docs/research/blur-phase-0/`) showed that a synchronized sub-surface and its parent's content reach the compositor in one transaction (Smithay `transaction.rs:261-278`) and that the blur then follows the scroll without lag, above and below the parent, at 1x and 2x.
Rejected: a blur drawn by the client as the shipping path (two places for Reduce Transparency, two blur algorithms); `ext-background-effect-v1` on sub-surfaces (KWin, Hyprland and niri ignore their regions, and it has no material, strength or soft edge); reading the region of the root surface for the in-window blur (it meets the wallpaper path); one surface with partial alpha (the compositor cannot tell chrome from content).
Decided by the owner on 2026-11-22: the criterion for the in-window blur is the frame time of the band pass at 2x for a 96 px band on a real GPU. A median of at most 1.0 ms passes, over 2.5 ms stops, and no frame of the 40 may reach 8.33 ms; between 1.0 and 2.5 ms the owner decides then ([runbook](research/blur-backdrop-design.md#10-gpu-runbook-the-frame-time-of-the-band-pass)). That frame time is NOT measured.
Decided by the owner on 2026-11-22: M2 and K3 start before the GPU frame time is measured; the owner accepts the risk that the work is wasted if the GPU criterion fails; the criterion still decides whether it ships on by default ([order of execution](research/blur-backdrop-design.md#71-the-phases)).
Decided by the owner on 2026-11-22: the kit's own Skia backdrop blur is deleted at the end of the plan, and Malaysia applies the measured values in every shell component ([order of execution](research/blur-backdrop-design.md#71-the-phases)).
Pending: confirmation by the owner of the protocol's shape (physical `leading` and `trailing`, `automatic` left to the compositor, the glass styles inside `material`, `set_backdrop` winning over `ext-background-effect-v1`, the radius in logical pixels at every scale). To review when the measurements end: whether version 10 carries all of macOS's configuration (`state`, `isEmphasized`, `maskImage`, `tintColor`, `effectIsInteractive`, container `spacing`, SwiftUI `tint` and `interactive`) or must grow before Malaysia serves it ([design 9.3](research/blur-backdrop-design.md#93-to-review-when-the-measurements-end)). The blur values per material are being measured ([materials](research/macos-materials.md), [blur](research/macos-blur.md)); the extent at 2x on macOS and what `automatic` resolves to are not measured.
Code: `crates/infinity-protocol/protocols/infinity-window-style-v1.xml`, `crates/infinity-protocol/tests/window_style.rs`, [Backdrop design](research/blur-backdrop-design.md), [Who composes the blur](research/blur-ownership.md), [Phase 0](research/blur-phase-0/README.md)

## 0092 — In-window glass is a request
Date: 2026-11-21
Decision:
- Target, from phase 3 on of [the design](research/blur-backdrop-design.md#7-phases-and-the-first-experiment): `FullscreenBar::Glass`, `ProgressiveGlass`, `TopGlass` and `Material` draw no blur. The kit leaves the area transparent, draws its chrome on a synchronized sub-surface over the content and sends `set_scroll_edge` (`Glass` hard; `ProgressiveGlass` and `TopGlass` soft) or `set_backdrop` with `within_window` (`Material`). `GlassContainer` and `RoundButton` stay as they are until merging nearby glass has a design.
- Without a compositor that offers version 10 the kit draws the solid it draws under Reduce Transparency (`FullscreenBar::Solid`, the opaque `MEDIA.material_tint`). It keeps no blur path of its own.
- The requests go out before the commit that carries the buffer, from an outbox like `flush_glass`. The sub-surface stays synchronized.
- Kit goldens and doc shots show the solid. The tests of the blur live in Malaysia, on its headless renderer.
- Until phase 4 lands, `glass.rs` still draws the Skia backdrop blur and the chapters say so. No public kit name changes.
Why: the compositor composes every blur ([ADR 0091](decisions.md)). A buffer that holds content and chrome cannot be blurred under the chrome by the compositor, so the window needs two surfaces, which is the sub-surface tree.

## 0093 — The materials of a window are the layer stack macOS builds
Date: 2026-11-22
Decision:
- Each of the 14 `NSVisualEffectView.Material` values of the macOS 27.2 SDK is a `MaterialLook` per scheme and state (the six SwiftUI thicknesses are `MaterialSet`s too, with sigma 59.2; in a window that is not key only `.bar` becomes a solid): a Gaussian `sigma`, a `saturation`, a `veil`, a per-channel `cap` (light) or `floor` (dark) and, for `selection`, a `gain` and `bias`. They are the tokens `components.material.visual-effect.<material>.<light|dark>.<active|inactive|reduced|reduced-contrast>` (`MATERIAL_<NAME>_LIGHT` and `_DARK`), and `ctappearance::material::over` and `blur_region` are the reference function. The order is the layer stack's: blur, saturate about the Rec. 709 luma and clamp, veil, cap or floor.
- The blur is one Gaussian of sigma 27.6 px at scale 1 for every blurred material, in encoded values, run by macOS on a backdrop at one eighth of the resolution (`CABackdropLayer.scale` 0.125; SwiftUI 0.25, glass 0.5), which is why `inputRadius` 30 gives 27.6 and not 29.7. It sees only its own region and renormalises its weights at the border, as macOS does (`inputNormalizeEdges`), so nothing outside the region reaches the pixels inside; a compositor that samples outside fails the parity check.
- Inactive is a solid. Reduce Transparency turns every blurred material into a solid (`reduced`) and Reduce Transparency with Increase Contrast into another (`reduced_contrast`); Increase Contrast alone removes no blur. The tokens carry no state of `isEmphasized`: only `selection` changes with it, and emphasized it is the accent.
- The numbers act on the compositor's own output values. macOS mixes in the display's device space (wide gamut on the measured panel); the tokens are the numbers of that stack, not sRGB conversions of its result.
- Every number comes from the layer tree of the probe's own process and is validated against the pixels: the fit over the gray and six colour ramps has rms 0.62 and max 2.0 at worst. The chameleon layer (opacity 0.05) is not modelled: its share is under that error.
Why: the earlier fit of one veil and one cap per surface, over white, gray and black, read sRGB conversions of a wide-gamut mix as chroma and could not tell the saturation, the cap and the floor apart; the layer tree names each part and the ramps confirm the order. The windows' materials have no other source than the render server's stack.
Rejected: a sigma per material (the 36 fits lie within 0.3 px, std 0.1); Kawase passes as tokens (the compositor picks them for the sigma, [section 10.10](research/macos-materials.md#1010-for-the-compositor)); sampling outside the region; one `Thickness` for the 14 materials (their parameters differ).
Pending: confirmation by the owner that `sigma` is in logical pixels at every scale (scale 2 is not measured); the system switches of Reduce Transparency and Increase Contrast (the per-process flags were used); the chameleon layer; the glass of `NSGlassEffectView`, whose lens needs a shader of its own, and which macOS 27.2.1 uses for real popovers and menus (their windows hold `glassBackground`, not the `popover` and `menu` materials); the sheet, sidebar, title bar and tooltip as real controls; malaysia's Dual Kawase (3 passes, offset 3.0, sigma 16.8) does not reproduce the kernel: with the offset fitted to sigma 27.6 it stays within 2.0 levels but over the rms tolerance for the low-veil materials, and a Gaussian on a backdrop downsampled by 4 reproduces it within 0.1 level at about the same cost ([section 14](research/macos-materials.md#14-the-blur-algorithm-and-malaysias-dual-kawase-2026-11-22)); Malaysia was not compiled against these tokens.

## 0098 — A glass window is a content surface and a chrome sub-surface above it
Date: 2026-11-22
Decision:
- The kit side of ADR 0091 and 0092, first slice (K3). When the compositor offers `infinity_window_style_v1` at version 10 or later and `wl_subcompositor`, a window's glass is declared and the kit draws no blur for it. The kit binds the global at the lower of what the compositor offers and 10 (`window_style::bind`), so a version 9 compositor gets version 9 and the legacy path: `glass.rs` draws Skia exactly as before, no request newer than the bound version is sent, and no golden changes. The decision is per window, in a root context (`BackdropSupport`) like `GlassSupport`.
- **Above, not below.** The window's root surface, the `xdg_toplevel`, stays the content. Each glass is declared on a synchronized sub-surface above it, the chrome (`ChromeSurface`). The root keeps what the rest of the kit already relies on: popups and menus parent it, as do the window geometry, the fractional scale and its viewport, the opaque region, keyboard focus and IME. Phase 0 composed both layouts, and a chrome below would make the root a transparent shell that every one of those paths would have to learn; a root region on it would also meet Malaysia's wallpaper blur ([design 7.2](research/blur-backdrop-design.md#72-phase-0-results), finding 1).
- **What is chrome.** The container that holds a declared glass: a `Declared` leaf (what `TopGlass` and `Material` become) names its parent, and that parent's subtree draws on the chrome surface, above the material, as the elements put over a SwiftUI `.background(.material)` do. That is the layout the chapters already ask for: the glass is the first child of the element it sits behind. Containers nest by merging into the outer one. A container with nothing beside it in the tree is no chrome: nothing is drawn below its glass, and all the nodes would leave the content canvas. The strip is the union of the container's area and its glass areas, cut to the window, in whole logical pixels, and the compositor places it with `wl_subsurface.set_position`.
- **How Freya's render splits.** `RenderPipeline` of Freya 0.5.3 draws every node of `tree.layers` into one canvas and the kit does not fork it. `render_passes` takes the chrome nodes out of `tree.layers` (a cost proportional to the chrome, not the tree), renders the content, then puts back only each chrome's nodes for its own pass, and restores the map. `render_pass` shifts the canvas by the strip's origin and clears a chrome to transparent. A chrome draws above every node of the content, whatever layer the content has, and anything it paints outside its strip is cut.
- **One swapchain per surface.** Each chrome has its own `Graphics` on the window's `GraphicsShared` (the same code a popup uses): a `VkSurfaceKHR` and a swapchain for its `wl_surface`, and a `wp_viewport` where the root has one. A draw acquires the root and every chrome, renders, presents the chromes first and the root last, so the parent's commit applies the chrome's cached commit with its position and its requests: one frame, no tear (ADR 0091). A chrome that fails is dropped and its nodes draw in the content; a lost device recreates them.
- **The declaration is read from the tree, not from an outbox.** The leaves cannot use hooks, and the strip must be known before the render, so `collect` reads the laid-out tree once per layout. `Requests::of` turns a chrome into one `set_backdrop` (`within_window`, the first material and radius, the rectangles of the leaves relative to the strip; the compositor keeps 16) and one `set_scroll_edge` (the edge of the first leaf and its depth from the strip's edge to the bottom of the glass); `send_requests` sends only what changed, before the buffer, and removes with empty rectangles and a depth of 0. `GlassOutbox` and `KnobOutbox` stay for the declarations of components.
- **Input and focus.** A window is still one Freya app, and the kit maps nothing. Malaysia delivers every pointer and touch event of a toplevel to its root surface in window coordinates, even over a chrome (`WindowStore::surface_under` never hit-tests sub-surfaces; M2, 2026-11-22), and keeps keyboard focus on the root. So the strip answers through the same tree, resize band, cursor shape and press serial as the rest. The first commit of this slice (`4936435866a3`) mapped events of a chrome sub-surface into the window (`at_in_window`, `Runtime::window_of`); no compositor that offers version 10 sends them, so the mapping was removed as unused. If Malaysia starts giving a sub-surface pointer focus, the kit must map it again from that commit, or the strip stops answering.
- **Elements.** `TopGlass` declares a soft top scroll edge as deep as its metrics (`FULLSCREEN_GLASS.height`). `Material` declares `set_backdrop` with `MaterialStyle::material`, whose Tengen value is `HudWindow`, and with the corner radius it was given. Both paint nothing, so the kit's tint, blur, rim and line are not drawn in this mode and the compositor draws its measured material. Under Reduce Transparency they stay the kit's opaque solid, as before.
Why: a buffer that holds the content and the chrome cannot be blurred under the chrome by the compositor (ADR 0092), and a sub-surface above an unchanged root changes the least of what already works. Rendering the chrome apart costs one traversal of the chrome nodes. The container rule needs no new API: it is the layout `Material` and `TopGlass` already document.
Rejected: a chrome below the root (see above); the chrome as large as the window with partial alpha (a second full-window buffer every frame); a strip sized by a declared rectangle instead of by the container (the content drawn over the glass would fall outside it); a layer threshold for the split (Freya layers are relative to the parent, and what sits over a glass is its container's children); forking Freya's `RenderPipeline` (the owner's decision on patching or forking Freya is open); an outbox for the leaves.
Pending: confirmation by the owner of the chrome above the root and of `HudWindow` as the material of `Material` (not measured against the kit's `MEDIA` look; `Thickness` is still not mapped). Not done in this slice: `FullscreenBar::Glass` and `ProgressiveGlass` and the rail over the content (their glass fades with the focus bar and version 10 has no way to fade a material), `GlassContainer` and `RoundButton`, drawing and presenting a chrome only when its nodes change (today both surfaces draw every frame), keeping the swapchain while a strip's size animates, more than one material or scroll edge per chrome (and Malaysia serves 4 requester surfaces per toplevel, and a chrome's material does not blur another's). Not verified: the draw, the swapchains and the commit order with a real compositor and GPU, and the hover over the strip, which needs Malaysia's M2 on the owner's laptop ([chapter 18](barrierkit/18-platform.md#glass-over-the-windows-content)); that Mesa's Wayland WSI commits a sub-surface inside `vkQueuePresentKHR` and does not throttle a synchronized one with its own frame callback.
Code: `crates/bk/src/platform/backdrop.rs`, `crates/bk/src/platform/chrome_surface.rs`, `crates/bk/src/platform/window_style.rs`, `crates/bk/src/platform/surface.rs`, `crates/bk/src/glass.rs`, `agents/recipes/glass_window.rs`, [Backdrop design](research/blur-backdrop-design.md), [Backdrops and media](barrierkit/15-backdrops-and-media.md), [Platform](barrierkit/18-platform.md)

## 0102 — A change moves with an `Animation` set by `with_animation`; a spring carries its velocity; parity is a curve error against a 60 fps recording
Date: 2026-11-22
Decision:
- **Parity (O1).** A transition of the kit matches the real one when the progress curve, sampled at 60 fps, differs from the recording by at most 0.02 of the travel after the start is aligned within one frame. The curve of the real one is fitted to the frames and the check is a test (`crates/bk/tests/kit/motion.rs`), not a judgement by eye. The first references are SwiftUI's own critically damped spring, sampled by a probe (0.0139 of the travel against the model, which is the frame jitter), and the table of [UIKit animations](research/uikit-animations.md#2-motion-table). A recording of a live kit window cannot meet 0.02: a frame shows the screen at an instant known only within the 16.7 ms step, so the floor is the largest change of the curve in half a step, 0.056 of the travel for `ω0` 18.26 (0.07 for 22.9). The live check uses that floor and stays manual (it needs the screen).
- **Spring (O2).** `animation::Spring` keeps `duration` and `bounce` as SwiftUI's `Spring(duration:bounce:)` does: `duration` is the perceptual period (`ω0 = 2π / duration`), `bounce` is `1 - ζ`. It gains an initial velocity (`Spring::with_velocity`, in units per second) and a settling duration, where the value is within 0.001 of the travel; the value is exactly the target after it. `Animation::Spring` is the same spring for the styles. The old curve (`ease_out` for `bounce` 0 and a damped cosine for more) is gone. Every measured UIKit spring is critically damped, so `bounce` is 0 in all the tokens.
- **Interruption.** A value retargeted while it moves starts a new spring from the value and velocity it shows (`use_animated`). For a spring this is exactly what SwiftUI does: a probe interrupted `Spring(duration: 0.344, bounce: 0)` at 0.127 s and the value went on up to its peak 11 ms later at velocity 6 per second before it came back, 0.0135 of the travel from the model that carries the velocity. A timed curve (`Ease`, `Custom`) restarts from the shown value with no velocity; SwiftUI measured the velocity carried there too (an ease in-out interrupted at 0.39 s peaked 0.31 s later and ended 1.00 s after the interruption: the old animation goes on and the new one is added), and the kit does not copy that.
- **Names (O4).** SwiftUI's: `Animation` (the existing `styles::Animation`, extended), `with_animation` and `Transition`. `with_animation(animation, body)` runs `body` and tags the turn with `animation` (`Animation::None` is `withAnimation(nil)`); the **outermost** call of a turn wins.
- **Transaction.** A `use_animated` whose target changes within 100 ms of a `with_animation` uses its animation instead of the style's; reduced motion turns it into `Animation::None` (0 ms, as `use_reduced_motion` does for the styles). A change with no transaction uses the style's animation, as today. The pure parts are `animation::effective` and the spring.
- **What SwiftUI does that the kit does not.** The probe (`swiftuitx`, one run, 60 Hz) shows that SwiftUI scopes a transaction to the writes in its closure: in `withAnimation(.linear(1.0)) { a; withAnimation(.linear(0.4)) { b }; c }` `a` and `c` took 1.01 s and `b` 0.41 s; `withAnimation(nil)` inside made `b` jump in one frame; a write outside the closure in the same turn jumped while the one inside took 0.5 s. Freya's `State` has one write path the kit cannot tag, so the kit scopes per turn: an inner call is ignored.
- **Transition.** `Transition` is SwiftUI's name for how a view enters and leaves (`opacity`, `scale`, `move`, `slide`, `asymmetric`). It is a value of opacity, scale and offset at `identity` and at `active`, applied by a kit-owned element that keeps a removed child mounted until its spring settles (T7: an `ElementExt`, no fork). It is not built here: its first user is navigation and presentation (U5), and opacity of a whole subtree needs the subtree hook (P1, [Shader needs](research/shader-needs.md)); Freya has one handler per event and a flat renderer, so the element draws the child itself.
- **Pacing (2026-11-23).** On macOS the display link's frame first steps the animations (Freya's ticker, then the runner's poll) and then draws, so each frame shows them at its own refresh. `use_animated` and the kit's other timed values read the time since they started (`animation::Clock`), not Freya's sum of whole milliseconds per frame, which ran 250 ms in about 278 ms at 180 Hz with steps of 4 to 6 ms. The runner polls Freya's `handle_events` again after each update until it waits: it returns on dirty scopes before it polls the woken tasks or registers its waker, and the animation then froze midway until the next input. A chrome whose only change is its origin moves its native views instead of building them again. AppKit's sidebar follows Core Animation's `easeInEaseOut` over 250 ms (a 180 Hz capture of the SwiftUI twin, three runs, 0.022 of the travel against 0.054 for the cubic ease-out), so `SplitViewStyle::animation` uses `ease_in_ease_out`.
- **Tokens (O3).** The measured durations and springs of the table are in `tokens.json` beside the existing ones: `duration.list-row`, `menu-close`, `popover-in`, `popover-out` and `spring.sheet-duration`, `alert-duration`, `push-duration`.
Why: the kit's one curve started faster and stopped harder than the measured ones (50 % at 52 ms against 92 ms, 99 % at 196 ms against 364 ms for 250 ms against `ω0` 18.26), and it could not carry a velocity, so a state flipped midway jerked. The physical model makes both the measured curves and the interruption exact and is the one SwiftUI documents.
Rejected: a physical model beside the old curve (two meanings of `Spring`; no style used the old one); stiffness and damping in the API (O2 chose duration and bounce); the additive layers SwiftUI uses for interruption (a spring needs none, and a timed curve is rare in the measured table); tagging every write with an `Animated` state wrapper (a second state type for every control; revisit if per-write scopes are asked for); a global transaction stack read at render (it would outlive its writes); building `Transition` without a user.
Pending: per-write scopes; `Transition` and the element that keeps a removed child (U5); the old `SPRING_DAMPING` token has no reader in the kit after this and stays for the other repositories; which of the kit's own `Ease` durations should become the measured springs (only the sidebar section is moved here); reduced motion for UIKit (not measured); the 100 ms window of the transaction is a choice, not a measurement; the live check of O1: the `with_animation` recipe with a red fill, run on the macOS runner (debug build, a 180 Hz display) and recorded at 60 fps twice, reached 50 % at 76 ms and 90 % at 218 ms against 92 and 213 ms of the spring and differed from it by 0.051 and 0.045 of the travel, inside the floor of 0.056 and not a defect of the curve. The pacing is in **Pacing**; `AnimNum` and `Spring` in an app's own `use_animation` still count whole milliseconds per frame.

## 0104 — A trackpad scroll owns the offset past the edges: a measured deceleration, a rubber band and a bounce
Date: 2026-11-22
Decision:
- **Semantics.** A continuous scroll (a touchpad: `WheelSource::Pixel` with its phase) moves the content 1:1 inside the range. Past an edge the content stretches by `over = d (1 - 1 / (1 + 0.07 x / d))` (`x` the input past the edge, `d` the view length). On release the content decelerates with the path and stop distance measured on a Mac Catalyst `UIScrollView` ([UIKit animations, section 6](research/uikit-animations.md#6-scroll)): `y(t) = D (1 - (1 - t/T)^4)`, `D = 157.5 v^(4/3)` pt, `T = 4 D / v`, `v` in pt/ms. A release beyond an edge returns on a critically damped spring (`w` 12 rad/s); a deceleration that reaches an edge continues into the band with 0.3 of its speed and returns the same way. A mouse wheel (`WheelSource::Line`) is as before: stepped, smoothed by Freya, no band.
- **Element (T7).** The kit scrolls with its own element, not with a fork: `ScrollView` wraps Freya's scroller in a clipping `rect` whose content is shifted by the overscroll, and a wrapper inside the scroller takes the touchpad wheel before Freya's handler sees it (it stops the event). The rest offset stays in Freya's `ScrollController` (so `reveal_y`, `scroll_to_x` and `VirtualScrollView` keep working); the overscroll, the release velocity and the deceleration are the kit's. `List`, `OutlineView` and `TextEditor` get it through `ScrollView`; `Table` takes the same wrapper around its `VirtualScrollView`.
- **Pure model.** `crates/bk/src/scroll_physics.rs` has no Freya types: a velocity tracker over the last 100 ms, `Fling`, `rubber_band` and `Bounce` are closed forms of the elapsed time, so a test calls them without a clock and the element evaluates them like `use_animated` does (no stepping, no `animation.rs` change).
- **macOS.** The system sends its own momentum as scroll events (`momentumPhase`), so there a release runs no deceleration: only the band and the return act.
- **Reduced motion.** With reduced motion the band and the bounce are off: the content stops at the edge and a release does not glide.
- **Pull to refresh.** `ScrollView::refreshable(refreshing, action)` calls `action` once when a pull at the start reaches 80 (UIKit fires at about 81, with the finger down); while `refreshing` is true the start edge is 60 above the content (UIKit's inset grows by 60) and a spinner shows in the gap; when it turns false the content returns on the same spring. The pull uses a looser band (0.5) than any other stretch, because the Mac band of 0.07 needs about 1300 pt of travel to reach 80.
Why: Freya clamps the offset and flings at `0.5 s * v` with its own smoothing; the measured stop distance is not linear in the velocity (0.2 s * v at 2 pt/ms, 0.37 s at 13 pt/ms) and the owner reported "no bounce, no inertia". The curve is exact for four flicks (0.5 to 1.8 % of `D`).
Rejected: forking Freya's scroll view (T7); a Freya `ScrollController` that allows an offset beyond the range (its clamps are in the view, and its fling would still run); an exponential with the documented 0.998 (the measured stop distance is 0.4 of it and `decelerationRate` has no effect on this path); the iOS rubber-band constant 0.55 (the Mac measured 0.07).
Pending: the touch path of `UIScrollView` and a real trackpad (not drivable by posted events); Weather's recording; a horizontal axis measured apart (the same model is used); the smallest flick that glides (Freya's 50 pt/s kept); the loose band of the pull to refresh (three pulls measured, not fitted); two view sizes for `d`.
Code: `crates/bk/src/scroll_physics.rs`, `crates/bk/src/scroll.rs`, `crates/bk/src/views/table.rs`, [UIKit animations](research/uikit-animations.md), [Views](barrierkit/11-views.md)

## 0105 — The gesture layer is SwiftUI's, over Freya's pointer events, with a pure arena
Date: 2026-11-22
Decision:
- **Names (O5 a).** `TapGesture`, `LongPressGesture`, `DragGesture`, `MagnifyGesture` and `RotateGesture` in `bk::gesture`, with `.on_changed`, `.on_ended` and `.updating` (`@GestureState` as `use_gesture_state`); the modifiers `.gesture`, `.simultaneous_gesture` and `.high_priority_gesture` of `ViewModifiers`; `.exclusively` and `.simultaneously` put gestures together and `.sequenced_before` makes a `SequenceGesture`, whose value is `First(a)`, then `Second(a, None)` and `Second(a, Some(b))`; the second starts from the press that is still down, or from the next press when the first ended on a release. The states are `UIGestureRecognizer.State`'s.
- **Pure recognizers.** Each gesture is a state machine over `Input { id, phase, at, time }` with no Freya type: tests feed it a table of inputs. A long press and a double tap report a `deadline`; the element arms a task on Freya's ticker and wakes the window at the deadline with `Timers::after`, since the ticker only runs after a drawn frame. The defaults are `ctdesign::GESTURE`: measured on SwiftUI on this Mac (tap 4 pt and 330 ms from a release to the next press with no distance limit, long press 500 ms and 10 pt, drag 10 pt; [U6 design](research/uikit-roadmap.md#u6-design-the-gesture-layer)) and, for magnify (0.01) and rotate (1 degree), SwiftUI's documented values.
- **Arena.** SwiftUI's rule: the deepest wins, a high-priority one beats its descendants, a simultaneous one neither wins nor loses, a winner waits while a gesture that outranks it can still begin. The element applies it per pointer in a thread-local registry: each gesture registers when the pointer goes down (the event bubbles from the deepest view), a gesture that begins claims the pointer and the others fail, a gesture that outranks another and can still begin holds the other's delivery, and a high-priority gesture holds every normal one until it fails.
- **One handler per event.** Freya keeps one handler per event on a node, so two `.gesture` calls would replace each other; gestures on one view are put together with `a.exclusively(b)` or `a.simultaneously(b)`, which share the node's handlers.
- **Pointers.** A mouse is pointer 0 and a finger is `finger_id + 1`; the handlers are `on_pointer_down` and the global move and up, so a drag that leaves the view still ends. Magnify and rotate take two fingers. A trackpad pinch (macOS `magnifyWithEvent:` and `rotateWithEvent:`) is `gesture::trackpad`: it gives the gestures that are under the pointer two fingers `TRACKPAD_FINGER` apart in a span of 100 pt, scaled by the sum of the magnifications and turned by the sum of the rotations, so the recognizers need no change and no Freya touch event is made (a touch would press buttons and scroll lists under the fingers). Wayland needs `pointer-gestures-unstable-v1` in the runner; `smartMagnify` has no gesture.
Why: gap 15 and D5; the scroll element's touch pan, a clone's long press and drag, and pinch zoom need recognizers and a rule for who wins a pointer.
Rejected: raw events only (every control would rebuild click, drag and long-press); gestures as a fork of Freya's events; arbitration by the order handlers run (the global events reach a parent before its child, so the registry orders by the down event).
The scroll view's touch pan is a `DragGesture::touches_only()` on its content (Freya's own touch pan is off there), with a band of 0.55 that is not measured. Pending: the 150 ms delay of a touch to a child (not measured; Freya has no way to hold an event back); the touch pan of `Table`; the trackpad pinch in the Wayland runner and its check on a real trackpad (a pinch cannot be posted, so the macOS mapping is tested through `gesture::trackpad`, not through an `NSEvent`); `SpatialTapGesture`'s location in the first value; a high-priority gesture that begins after a descendant has delivered (it cannot take it back); the latency of SwiftUI's long press (about 0.12 s after the duration) and the rule of its double tap.
Code: `crates/bk/src/gesture.rs`, `crates/bk/src/modifiers.rs`, `crates/bk/tests/kit/gesture.rs`, [Gestures](barrierkit/05-controls.md#gestures), [U6 design](research/uikit-roadmap.md#u6-design-the-gesture-layer)

## 0106 — `alert` and `popover` take a `State<bool>`, as `sheet` does; `onHover` and `onTapGesture` are modifiers
Date: 2026-11-22
Decision:
- `ViewModifiers::alert(is_presented, || Alert)` shows the alert while the `State<bool>` is true. Every button, Enter and Escape write `false` after their callback, because "all actions in an alert dismiss the alert after the action runs" (Apple, `View.alert(_:isPresented:actions:)`). A hand-built `Alert` still does not close itself.
- `ViewModifiers::popover(is_presented, size, || content)` opens a `Popover` at the view's area once it has one, writes `false` when the compositor dismisses the popup (`PopupSpec::on_dismissed`) and closes the popup when the app writes `false` or the view leaves the tree. `Popover::show` returns its `PopupId` and `Popover::on_dismissed` sets the callback.
- `ViewModifiers::on_hover(|inside| ..)` and `on_tap_gesture(count, |_| ..)` are `onHover(perform:)` and `onTapGesture(count:perform:)`. Both sit on Freya's pointer enter and leave events, which a node holds once, so a view that has one cannot have the other or a gesture.
Why: ADR 0085 gave `sheet` a `State<bool>` and no `Binding`; the same shape serves the other two presentations. The gap study ranked a binding-driven presentation 8th and `onHover` and `onTapGesture` among the most written modifiers.

## 0109 — A scroll position is a value the app sets and the view writes back; shapes draw on a canvas and clip through Freya's rounded rectangle
Date: 2026-11-22
Decision:
- **Scroll position.** `ScrollPosition` is SwiftUI's value: `at(x, y)`, `edge(Edge)` and `id(id, anchor)`, with `point()` and `is_positioned_by_user()`. `ScrollView::scroll_position(State<ScrollPosition>)` follows ADR 0085 (a `State`, no `Binding`): the view scrolls to what the app sets, and a scroll by the user writes `at(..)` back with `is_positioned_by_user()` true, which the view does not apply again. A set inside `with_animation` animates (the transaction of ADR 0102, `animation::transaction_at`); `ScrollController::scroll_to(position, animation)` takes the `Animation` as an argument because a transaction is tagged after its closure ends. The animated path is the `Animation::progress` of the style layer, on Freya's ticker.
- **Ids.** `.id(String)` (`IdentityModifiers`) wraps a view in a component that reports its area to the nearest `ScrollView` through a context; the offset is the area less the content's origin. A `String` stands for SwiftUI's `Hashable`. The anchor is torin's `Alignment` (`Start`, `Center`, `End`: 0, 0.5, 1 of view and viewport); `None` scrolls the least that shows the view (`revealed_offset`). An unknown id does nothing.
- **Callbacks.** `on_scroll_geometry_change(ScrollGeometry { content_offset, content_size, container_size })` and `on_scroll_phase_change((old, new))`. `ScrollPhase` is `Idle`, `Tracking`, `Interacting`, `Decelerating`, `Animating`. The state of the glide and of the stretch moved into `ScrollController` (same code, ADR 0104's physics are untouched) so that `scroll_to` ends a glide first; a touch ends a programmatic animation.
- **Shapes.** `Rectangle`, `RoundedRectangle` (the continuous corner of ADR 0101 and `CORNER_SMOOTHING`), `Capsule`, `Circle`, `Ellipse` and `Path` (`move_to`, `add_line`, `add_curve`, `close_subpath`) are views that draw on `canvas::Canvas`: Freya has no path element, and its `rect` cannot draw an ellipse or a circle in a frame that is not square. `fill(ShapeStyle)` and `stroke_border` resolve the style as `background_style` does; a gradient or a backdrop is a render callback, which the painter masks by the path's coverage in a layer.
- **Clip.** `ShapeModifiers::clip_shape(styles::Shape)` sets the `corner_radius` and `overflow(Clip)` of the view: `styles::Shape` already is SwiftUI's `.capsule`, `.circle` and `.rect(cornerRadius:)`, and it takes `UnevenRoundedRectangle` too. A capsule and a circle use a radius no frame reaches, which Skia scales to the frame.
Why: items 5 and 9 of the gap list.
Shortcuts and limits:
- An ellipse or a `Path` cannot clip: Freya's `clip` is `clip_rrect` of the element's corner radius, and an arbitrary clip needs a kit-owned container element (T7).
- Freya clips with the circular rounded rectangle even when it draws the continuous corner, so a continuous clip follows the circular curve of the same radius, not the continuous one (the difference is not measured).
- A circle clip of a view that is not square is a capsule; the `Circle` view is centered.
- `stroke_border` is `strokeBorder`; SwiftUI's centered `stroke` would be cut by the canvas at the frame, so only `Path` has `stroke`. A `ShapeStyle::Material` fills with its tint and does not blur. `ConcentricRectangle` is not built.
- `Tracking` is set when a gesture begins and replaced in the same event, so no callback sees it. A mouse wheel gives no phase, and on macOS the system's momentum counts as `Interacting`. `scrollTargetBehavior`, `defaultScrollAnchor`, a position set before the first layout (an id is not measured yet) and a view id written back as the user scrolls (a point is written) are not built.
- Two views that share a controller share the stretch and the glide.
- Every `.id` view gets a layout notification per scroll frame; use it on rows, not on thousands of cells.
Rejected: a handle that carries an id table the app fills (the context needs nothing from the app); `scrollTo` reading the transaction inside its closure (the transaction is tagged after the closure ends); drawing shapes with `rect` and a radius (no ellipse, circle in a square frame only); a kit-owned clipping container now.
Pending: a visual check of a continuous clip against the system's; `scrollTargetBehavior(.paging)`; arbitrary clips (T7).
Code: `crates/bk/src/scroll/position.rs`, `crates/bk/src/scroll.rs`, `crates/bk/src/shapes.rs`, `crates/bk/tests/kit/scroll.rs`, `crates/bk/tests/kit/shapes.rs`, `agents/recipes/scroll_position.rs`, `agents/recipes/shapes.rs`, [Scrolling](barrierkit/05-controls.md#scroll-position), [Shapes](barrierkit/05-controls.md#shapes)

## 0118 — On macOS AppKit composes every blur and glass, and SwiftUI is the reference
Date: 2026-11-23
Decision:
- On macOS the kit draws no blur or glass of its own. Each declaration that [ADR 0091](decisions.md) sends to Malaysia as a request becomes the native view that composes the same effect in WindowServer: an `NSVisualEffectView` for a material, an `NSGlassEffectView` (in an `NSGlassEffectContainerView` when shapes merge) for Liquid Glass, an `NSSplitViewItem` for the sidebar and inspector panes, an `NSPopover` for a popover, AppKit's own window background, and AppKit's own title bar under a bar that no scroll view reaches. [Backdrops and media](barrierkit/15-backdrops-and-media.md#on-macos) lists each one.
- The kit's Metal layer draws the content and the ink over the glass: text, symbols, and the selection, hover and pressed colors. Those colors are measured against a SwiftUI twin on the same macOS, in light and dark.
- SwiftUI on the running macOS is the reference. Each piece is compared with its SwiftUI twin at the same frame. What no public AppKit API reproduces is recorded as a ceiling, not imitated with a shader.
- The kit calls AppKit from Rust through `objc2` and holds no Swift code. Interactive glass (`effectIsInteractive`) needs macOS 27. Before macOS 26 there is no `NSGlassEffectView`, and the controls paint their own fill.
- An app may still add its own effects on top of the system's (`GroupEffect`, a Skia shader). They are extras; the system's materials are never redrawn by the kit.
Why: the kit gives apps the look and behavior of their desktop, as SwiftUI does on macOS. When one owner, the compositor, draws every blur, every app stays in step with the desktop. The radius, the wallpaper tint, Reduce Transparency, Increase Contrast and the look of each new release come from the system, the same in every app, and the glass never lags the content. macOS offers that owner through public views. Malaysia offers it on Linux through `infinity_window_style_v1` ([ADR 0091](decisions.md)). So one declaration in the kit maps to the same model on both systems, and the macOS port is the test that the model holds. Liquid Glass recreated in Skia would drift with each macOS release and could not match the lens, the wallpaper tint or the system settings.
Rejected: Freya or Skia shaders for the system's materials (a second implementation that drifts from the system); Swift or SwiftUI code inside the kit (a second language and build step for what AppKit already gives). Swift is to be considered again only for an effect that exists only in SwiftUI, such as `glassEffectID`, `glassEffectUnion` and `glassEffectTransition`.
Pending: the ceilings measured on 2026-11-23:
- a held knob's lens fills with the track;
- the scroll edge under the bar over kit content;
- the glass morph transitions.

The press feedback on macOS 26 is not verified.

## 0113 — A transition runs on a `Presence` that keeps the leaving view; `glassEffect` is a one-item `GlassContainer`
Date: 2026-11-23
Decision:
- **Transition.** `Transition` is the look of a view that is gone, on the way in and on the way out: `OPACITY`, `SCALE`, `IDENTITY`, `scale(s)`, `offset(x, y)`, `move_edge(Edge)` (one of the view's own widths or heights beyond the edge, left to right), `combined(other)` (opacity and scale multiply, offsets add) and `asymmetric(insertion, removal)`. The value at progress `p` is the rest look mixed with the gone look by `1 - p`; a spring that overshoots may overshoot a scale, and opacity is clamped.
- **Presence.** `Presence::new(Option<view>).transition(t)` is the smallest mechanism that keeps a removed view mounted: a component that stores the last child, renders it while its progress is above 0 and then renders nothing (an absolute empty node, so a stack's spacing does not count it). Its progress is `use_animated(present, Animation::None)`, so a transition runs inside `with_animation` (the transaction of ADR 0102) and a change without one is instant, as in SwiftUI; a toggle midway keeps the value and the velocity shown. A view present at first mount does not animate in. The wrapper sets `opacity`, `scale` and `offset_x/y` of Freya's rect and `interactive(false)` while the view leaves. `move_edge` needs the view's size, read with `on_sized`; until it is read the view is transparent, so it does not flash in place.
- **Content transition.** `ContentTransition::{Identity, Opacity}` and `.content_transition(t)` on any view. A change is found by comparing the element with the last one (`Element: PartialEq`); two `Presence` slots alternate, the one that leaves lies over the one that enters (absolute), so the size is the new view's.
- **`use_animated` fix.** Freya restarts the clock of `use_animation_transition` one render after the serial changes, and that render read the old clock, finished, so `use_animated` returned the target for one frame (a removed view vanished, an inserted one flashed whole). The render after a retarget with a duration now holds the value shown.
- **glassEffect.** `.glass_effect(Glass, Shape)` (`StyleModifiers`) is a `GlassContainer` of one item: on macOS 26 and later the existing native path declares an `NSGlassEffectView` behind the view and the view draws in the chrome above it; below 26, or under Reduce Transparency, it is the kit's blur or opaque solid. `Glass::REGULAR` and `CLEAR` are `Glass.regular` and `.clear`. The radius is the shape's; a capsule uses a radius no frame reaches, which the item caps at half its height; a circle is the largest one centered in the view; an uneven shape takes its largest corner. Each glass of a chrome is its own native view with its own radius and variant (`Chrome::glasses`), so nested glass composes, and a chrome with spacing 0 uses no `NSGlassEffectContainerView`. Reduce Transparency makes a regular glass the toolbar's plain fill (`resolved().toolgroup.bg`). Measured against SwiftUI in [glass-effect-comparison.md](research/glass-effect-comparison.md): 0 levels at the centre and the rim, key and not key, light and dark.
- **Chromes.** `MOST_CHROMES` is 8 on macOS and 3 on Linux (`platform/macos/mod.rs`, `platform/linux/mod.rs`). Malaysia serves 3; on macOS a chrome is one Metal layer and one set of native views, and `glassEffect` makes one per view. Linux is unchanged.
Why: items 6 and 11 of the gap list. Both reuse what exists: `use_animated` and the transaction for the first, the native glass path of ADR 0100 for the second.
Rejected: a modifier that makes any view animate its own removal (a Freya component cannot see its parent drop it; only a component that stays mounted can); a `matchedGeometryEffect` built on a registry of window areas filled by `on_sized` (a view appears at its new place for one layout before it can start from the old one, and a size change would not animate with layout); per-glyph `numericText`; a native glass per view in a new platform function (the one-item container already does it).
Pending: `matchedGeometryEffect` and `matchedTransitionSource`; `numericText` and `interpolate`; `slide`, `push`, `blurReplace`; right-to-left `move_edge`; `Glass.tint`, `.interactive()`, `glassEffectUnion` and `glassEffectTransition` (a tint is a new `WireMaterial`, so a change of the compositor protocol); nested glass of another radius or variant on Linux (the wire holds one of each, ADR 0100); more than 8 glasses a window; an uneven shape with its own corners (`NSGlassEffectView` has one `cornerRadius`); the Reduce Transparency and Increase Contrast glass (SwiftUI's shows the blurred backdrop and a rim, the kit's is a flat fill; clear is a dark plate); macOS below 26 (not run; evidence in the comparison); scale 2.
Code: `crates/bk/src/transition.rs`, `crates/bk/src/animation.rs`, `crates/bk/src/modifiers.rs`, `crates/bk/src/glass_container.rs`, `crates/bk/src/platform/backdrop.rs`, `crates/bk/tests/kit/transition.rs`, `crates/bk/tests/kit/glass_effect.rs`, `agents/recipes/transitions.rs`, `agents/recipes/glass_effect.rs`, [Transitions](barrierkit/14-animations.md#transitions), [Glass on any view](barrierkit/15-backdrops-and-media.md#glass-on-any-view)

## 0112 — Accessibility modifiers by SwiftUI name reach VoiceOver; a file dialog is a sheet of its window; a document asks before it closes
Date: 2026-11-23
Decision:
- **Modifiers.** `AccessibilityModifiers` is implemented for every view that has Freya's `AccessibilityExt`: `accessibility_label`, `accessibility_hint` (`description`), `accessibility_value`, `accessibility_hidden`, `accessibility_identifier` (`author_id`), `accessibility_element(AccessibilityChildBehavior::{Ignore, Combine, Contain})` and `accessibility_add_traits(AccessibilityTraits::IS_BUTTON | IS_HEADER | IS_LINK | IS_IMAGE | IS_STATIC_TEXT | IS_SELECTED)`. `forward_overrides!` (every control built on `Overrides`) now forwards `AccessibilityExt` and `Overrides::apply` merges the modifiers' node into the control's own, so `Button`, `TextField` and the 40 other controls take them; `Text`, `HStack` and the other `forward_element!` views already did.
- **Freya rewrites the label.** `AccessibilityTree::create_node` (`freya-core-0.5.3/src/accessibility/tree.rs:455-480`) replaces the label of every node that has text, or a first child with text, by that text. What a view asked for therefore travels in the node's `class_name` (`Marks`: label, child behavior, text field) and `resolve_marks` applies it to the finished tree, which is also where `Ignore` and `Combine` fold the subtree.
- **macOS bridge.** The kit had no accessibility on macOS: the tree was built and dropped. Each window now creates an `accesskit_macos::SubclassingAdapter` on its content view (`platform/macos/accessibility.rs`, `a11y` feature). VoiceOver and the AX API read it: role, title, value, help (the hint), identifier, frame, children, `AXPress` and focus. The adapter is lazy: until a client asks, the runner builds nothing; the first query gets the whole tree at once. A tree with marks is sent whole on every change.
- **Text input.** `TextField` and `SearchField` mark their wrapper; `resolve_marks` gives the input node the field's label (the modifier, else the placeholder), the typed text as value (empty when Freya shows the placeholder), the placeholder, and drops the nodes Freya draws inside it. `TextEditor` sets value and placeholder itself.
- **File dialogs.** `FileDialog::open()` and `::save(name)` with `.title`, `.allowed_content_types(Vec<ContentType>)` (`ContentType::Folder`, `ContentType::extension("png")`), `.allows_multiple_selection`, `.directory(path)` and `.present(&WindowControls)`; the modifiers `file_importer(State<bool>, types, multiple, on_completion)` and `file_exporter(State<bool>, name, types, on_completion)` call it, and `file_dialog_default_directory(path)` (environment) gives the start folder of the dialogs below it. On macOS the dialog is `NSOpenPanel` or `NSSavePanel` as a sheet of the window (`beginSheetModalForWindow`); a window the runner does not know gets a free panel. The completion runs only when the user chose. `portal::open_files` and `save_file` (the image well) use the same code through `panels::open_files` and `save_file`.
- **Documents (supersedes the close veto, quit and open-URL non-goals of [ADR 0085](#0085--no-binding-no-action-routing-or-app-lifecycle-callbacks) for documents).** `use_document(write)` returns a `Document`: `is_edited`, `set_edited`, `url`, `set_url` and `save()` (asks for a file when there is none, calls `write`). An edited document shows the dot in the close button and `NSWindow.representedURL`. A user close (the red light, Cmd-W) of an edited window is vetoed in `windowShouldClose:`; the kit shows an `NSAlert` sheet "Do you want to save the changes made to the document “name”?" with Save, Cancel and Don’t Save (Cmd-D), saves, and closes. Cmd-Q performs the same close on the first edited window and cancels the quit; the user quits again. `on_open_url(|OpenedUrl|)` receives the files and addresses that Finder, `open` and `open -a` hand the app through `NSApplicationDelegate.application(_:openURLs:)`; an event that arrives before a handler exists waits in a queue.
Why: items 4, 13 and 12 of the gap list; the owner asked for them on 2026-11-23, which is the "until an app asks" of ADR 0085.
Limits:
- macOS labels reach AXTitle, not AXDescription: `accesskit_macos` maps `label` to `accessibilityTitle`. `IS_HEADER` is role `Heading`, which `accesskit_macos` names `Heading`, not `AXHeading`. No `AXSelectedTextRange` and no per-character text for a field.
- `Ignore` keeps the text Freya took from the first child when the view has no label. `Combine` joins the labels and values of the subtree with ", ".
- The kit's own traffic lights (a `Plain` window) and `WindowControls::close()` close without asking: only the native close does (Cmd-W and Cmd-Q reach the same delegate methods but were not run). A dialog or a document on Linux is unchanged: the portal takes no parent, filters or start folder, nothing is vetoed, and `accessibility_element` is not applied (the AT-SPI path is untouched).
- A document is one per window; `on_open_url` goes to the first handler that renders. `write` runs on the main thread. A save that fails keeps the window open and logs a warning. `allowedFileTypes` (extensions) is the deprecated call that `UTType` replaces; it works on macOS 27.
- Filters are extensions only; `UTType` conformance (`.image`) is not built. There is no `fileExporter` that writes a `FileDocument`, no `DocumentGroup`, no autosave or versions, no recent-documents menu and no `Info.plist` generation: an app declares `CFBundleDocumentTypes` and `CFBundleURLTypes` itself for Finder to route files and links to it.
Rejected: a patch of Freya's label rewrite (pinned `=0.5.3`); a new accessibility tree for AppKit built from kit nodes (it duplicates accesskit); `NSDocument` (a second owner of the file and of the window); a `Binding` for `is_edited` (ADR 0085); showing the close alert in the kit's own `Alert` (the sheet of the system is what the user expects, and it is the platform's to place).
Pending: Linux (`xdg-foreign`, the portal's filters, an AT-SPI `Ignore` and `Combine`); `UTType` filters; `FileDocument`; a close that asks for every edited window when quitting; the kit's traffic lights asking; reading `AXValue` of a field after typing was not driven with a real keyboard.

## 0110 — A layout is a placement the kit applies after torin measures; `ZStack` and `ViewThatFits` build on it; a layout direction is a scope that mirrors kit views
Date: 2026-11-23
Decision:
- **`Layout`.** `Layout::place_subviews(proposal, sizes) -> Placement` is SwiftUI's `sizeThatFits` and `placeSubviews` in one call. `LayoutContainer::with_layout(layout)` is a custom element (like `Grid`, ADR 0089): torin measures the subviews as usual, then `ElementExt::post_measure` moves each by the origin the layout returned and sets the container's content size to `Placement::size`. All subviews but one are absolute children, so each is measured with the space the container has; `Layout::sizing_subview` (the first by default) stays in the flow, so a parent that centers the container sees that child's size and not zero.
- **`ZStack`.** `ZStack` is `LayoutContainer<ZStackLayout>`: the size is the largest child, `alignment` is `ContentAlignment`. `OverlayModifiers::overlay` and `background_view` are a `ZStackLayout` sized by one subview (the view): the content is placed in its frame and never sizes it. `background_view` and not `background`: Freya's `BackgroundExt::background` takes the name.
- **`ViewThatFits`.** A component that watches its own width (or height, `Axis`) with `on_sized` and renders the first candidate whose stated extent fits, or the last. `candidate(extent, view)` takes the extent because torin cannot measure a view before choosing it and a `Text` wraps to whatever it is given, so it always "fits"; the extent is the author's ideal size. Only the chosen candidate is built, so the accessibility tree holds one.
- **Right to left.** `LayoutDirection` defaults to `LeftToRight` and is an environment value (`State<LayoutDirection>`, so `use_environment::<LayoutDirection>()` reads it). `EnvironmentModifiers::layout_direction` is a scope that provides the value, sets `layout_direction` on the six control styles that have the field (`Theme` restyles, as `control_size` does) and mirrors the view it wraps. SwiftUI's measured behavior (`~/src/probes/rtlmirror.swift`, macOS 27.2): `HStack`, `Grid`, `ZStack`, `Form` label and content and `List` rows run from the right; `.leading` alignment of a `VStack`, a `frame` and a `Grid` is the right edge; `padding(.leading)` mirrors; a custom `Layout` is mirrored by SwiftUI itself, its `bounds` being flipped; multi-line `Text` aligns right.
- **How a view mirrors.** `resolve_mirrored` runs when `HStack`, `VStack`, `Frame`, `Label` and `Text` become elements (a stack reads the ambient direction there, in the component that builds it): a horizontal `rect` reverses its children and swaps `Start` and `End` on its main axis, a vertical one swaps them on its cross axis, a `label` with a width (not hugging its text, which Skia would draw shifted out of its box) and no explicit alignment aligns right. `Grid`, `ZStack` and `LayoutContainer` read it at the same point and flip their origins inside the container. `Form` and `Row` mirror the rects they build, the chevron and the trailing text field. A scope that wraps a view built before it (`view.layout_direction(..)`) flips the stacks, labels and containers of that built tree once, when the direction around the call differs; views inside components render below it and read the value themselves.
Why: gap rows 3 and 15. torin cannot give a child the size of its sibling or a reverse direction, but `post_measure` can move, so what the kit builds is a placement.
Shortcuts and limits:
- The container is sized from one subview for its parent; a parent that centers it places it by that size (the same limit as `Grid`). `Fill` subviews fill what the container was offered, not the base of an overlay. A `ZStack` with its own width keeps its children at the start.
- No `sizeThatFits` with several proposals, `layoutValue`, `ViewSpacing` or `AnyLayout`: torin measures each subview once.
- `ViewThatFits` has one frame of lag at the start (it offers 0 and shows the last candidate) and needs the extent of each candidate.
- Right to left: padding, margins and absolute positions are physical; `List`, `Table`, the sidebar, the title bar and the other kit components that build raw `rect`s do not mirror; a raw `rect()` mirrors only through a scope that wraps it; there is no `layoutDirectionBehavior`, no flipped symbol (only the `Form` chevron) and no direction from the locale. Freya never sets the paragraph direction, so bidirectional runs reorder but an RTL sentence keeps LTR punctuation placement.
Rejected: a torin fork or patch (pinned `=0.5.3`, not ours); a `Layout` that gets a measured size per proposal; measuring candidates in `ViewThatFits` through `hidden_children` (a hidden candidate stays in the accessibility tree and a `Text` always fits); rewriting every `rect` under a scope (it would flip kit components twice); a `Placement` of `Point2D` (the grid already returned tuples).
Pending: the `Form` and `Row` comparison with a probe is by positions only, not by pixels; `List`, `Table` and chrome mirroring; the language of the locale (`Locale.Language.characterDirection`); `flipsForRightToLeftLayoutDirection`.
Code: `crates/bk/src/layout/layers.rs`, `crates/bk/src/layout/fits.rs`, `crates/bk/src/layout/direction.rs`, `crates/bk/src/layout.rs`, `crates/bk/src/views/form.rs`, `crates/bk/src/modifiers.rs`, `crates/bk/tests/kit/layout.rs`, `agents/recipes/layout_layers.rs`, `agents/recipes/right_to_left.rs`, [Layout](barrierkit/11-views.md#layout), [SwiftUI API gap](research/swiftui-api-gap.md)

## 0111 — `Text` takes runs, inline Markdown and selection; the clipboard and a drag carry typed payloads
Date: 2026-11-23
Decision:
- **Runs.** `Text` keeps its `label()` and adds `Inline` (spans, selectable, line height, line limit). While the spans are empty and the text is not selectable, nothing changes. Otherwise `From<Text> for Element` builds `StyledText` (`styled_text.rs`), a component over Freya's `paragraph()` or `SelectableText` that takes the label's layout, effect, accessibility, handlers, key and text style. `Text + Text` starts from a default `Text::new("")` and gives each operand's spans only the style fields its author set (those that differ from the default), so a modifier on the sum reaches the fields no operand set and an inner `foreground_style` wins over the outer one, as in SwiftUI. `bold`, `italic`, `underline` and `strikethrough` are SwiftUI's `Text` modifiers.
- **Markdown.** `rich_text::markdown(source)` is a hand parser of the inline subset (`***`, `**`, `__`, `*`, `_`, `~~`, `` ` ``, `[title](https://x.org)`, backslash escapes) into text plus `StyleRun`s, the runs `TextEditor` already draws. `styled_spans` moved to `rich_text` and gives each span its link. `Text::markdown(..)` is explicit: `Text::new(..)` stays verbatim. A link opens through `portal::open_uri` on a click (the hit test of `char_under`) and shows the hand cursor. `RunStyle::strikethrough` is plan item 1 of `rich-text-plan.md`.
- **Selection.** `Text::text_selection(true)` renders Freya's `SelectableText`. Command+C and Ctrl+C copy because `AppInstance::text_field_focused` also accepts a focused `Role::Label`, which only a selectable text can be (it alone is focusable).
- **Typed payloads.** `DragPayload` gains `Html { text, html }` and `Image(png bytes)`. `pasteboard::Transferable` (`payload`, `from_payload`; `String`, `Vec<PathBuf>`, `DragPayload`) and `pasteboard::Pasteboard` (`general`, `named`, `copy`, `paste`) sit on `platform::pasteboard::{write, read}`: `NSPasteboard` items on macOS (`macos/pasteboard.rs`: text, HTML, PNG with a TIFF twin, a TIFF-only board reads as PNG, one file URL item per path, private boards), text only on Linux (`platform/pasteboard.rs`, false and `None` for the rest). `WindowControls::copy_rich` writes HTML on macOS. On Linux the payload is offered as `text/html` and `image/png` through the existing `mimes` and `bytes`.
- **Drag out on macOS.** The runner handles `StartDrag` by calling `ContentView::begin_drag`, an `NSDraggingSession` with the current mouse event, one `NSDraggingItem` per `NSPasteboardItem`, and an image under the pointer (the picture, the file icon or the `doc.text` symbol).
Why: items 2 and 7 of the gap list.
Shortcuts and limits:
- Markdown is inline only. A mark without its closing mate stays literal; `_` inside a word is literal; nesting of the same mark is not read.
- A span has one decoration: a link or an underline hides a strikethrough on the same run. A link in a selectable text does not open.
- A sum keeps the line height and paragraph options of the plain text it starts from, and drops the layout modifiers of its operands. `Text(Image)`, interpolation and `AttributedString` are not built; SwiftUI deprecated `Text + Text` in macOS 26 for interpolation, which Rust cannot do for views.
- `Text::markdown` links take the accent without an underline, as SwiftUI draws them; the editor underlines them.
- The code font is `MONO` after Menlo: Core Text has no `monospace` alias and Geist Mono is not on a Mac.
- The drag starts from the last mouse event of the window, not from the event that crossed the threshold, so a call made after another event type could be ignored by AppKit (not seen). The kit may get no mouse-up for a drag that AppKit finished (not checked), as on Linux.
- A drop target for typed data does not exist on either system (Linux accepts `text/uri-list` only; macOS nothing); neither do `copyable`, `cuttable` and `pasteDestination`, `.rtf`, `.pdf` and `.color` types, or images and files on the Linux clipboard. The read of an image on macOS has no size cap.
- The Linux side compiles against `freya_clipboard` only and was not built or run in this change.
Rejected: `pulldown-cmark` (a dependency for a 70-line subset); Markdown in `Text::new` (it would change every file name that holds an asterisk, and SwiftUI reads Markdown only in a literal); a kit-owned text element (Freya's `paragraph()` already has spans); a `Transferable` with content types and codecs (four payload shapes cover images, rich text, files and text, and an app type maps onto one of them).
Pending: a typed drop target (`registerForDraggedTypes` on macOS, any MIME on Linux); `copyable` and `pasteDestination`; the Edit menu on a selectable text; a drag started by a real pointer against TextEdit, Preview and Finder.

# AppKit gap

**Goal:** list what AppKit offers for designing macOS 27 apps and BarrierKit
lacks, rank the gaps by their weight on app design, and say what blocks each.
**Scope:** every class, protocol, enum, notification and option group a UI app
can use in the 305 files of `AppKit.framework/Headers` and in AppKit's Swift
interface, as Xcode 27.2 (macOS 27.2.1 SDK) ships them, against `bk` on `main`
at `7e8f243f`, 2026-11-21. It lists only what
[the coverage matrix](swiftui-appkit-coverage.md) does not list or lists
wrongly. It does not repeat the matrix's 218 rows, and it does not measure
looks: no probe ran.
**Reader:** whoever chooses what the kit builds next, and whoever builds it.
**Input:** the SDK headers, the kit's code and docs, the pinned `freya-*`
`=0.5.3` sources, the pinned `wayland-protocols` 0.32.13 and the portal specs.
**Output:** a row per AppKit item with a status, its evidence, and for each gap
the need, the Rust, Freya or Wayland equivalent, a size and a blocker; the
macOS 26 and 27 additions; a top 20; the decisions only the user can take.

## Steps

1. Read the [summary](#summary) and the [top 20](#top-20-gaps).
2. Read the [decisions](#decisions): each one blocks several gaps.
3. To work on a gap, open its [area table](#area-tables) and read the row.
4. To check a row, run its `rg` pattern from the repository root. A pattern
   that finds a hit means the row is out of date: fix the row.
5. When a commit closes a gap, change the row here and the matrix row in the
   same commit (`AGENTS.md`, «Documentación», rule 3), and add the
   [glossary](../barrierkit/20-glossary.md) row for each new public name.
6. To start a gap that has a [proposed matrix row](#proposed-matrix-rows),
   add the row to the matrix first.

## Method

Twelve readers each took one area of the headers (the Swift overlay was the
twelfth). Each wrote one row per class or family, with a status and the search
that backs it. The author sampled the claims against the code: `Instance::open`
drops its URIs, the runner closes a window with no veto, `start_drag` passes no
icon, `play_event_sound` has no caller, Skia's `pdf` feature is off,
`Atspi::new` runs only when a window is shown, the controls take
`&'static str`, `Symbol` has 124 variants, and `rg` finds no `concentric`,
`Grid`, `Spacer` or `tiled`. Each held.

Statuses (the matrix's [statuses](swiftui-appkit-coverage.md#statuses) differ):

| Status | Meaning |
|---|---|
| `implemented` | The kit has it. The row names the public item. |
| `partial` | The kit has part of it. The row says what is missing. |
| `absent` | The kit has nothing and the item applies to Linux and Wayland (the matrix says `missing`). |
| `n/a` | It does not apply on Linux or Wayland. The row says why. |
| `decision` | Out of scope by an ADR. Cited only when [decisions](../decisions.md) says so. |

Size: `S` a view or modifier over existing primitives, a day or two. `M` a
component with its own state, style and bench scene, about a week. `L` a
subsystem, a protocol, a compositor change or a measurement campaign, weeks.
Sizes are estimates; no code was written to test them.

Blocker: `none`, `Freya` (the missing piece and the file read), `Wayland` (the
protocol and its stage), `compositor` (malaysia must do it), `Skia`, `GPU`,
`D-Bus/portal`, or `measurement` (a macOS probe comes first).

The counts come from the SDK:

```sh
H=$(xcrun --show-sdk-path)/System/Library/Frameworks/AppKit.framework/Headers
ls "$H" | wc -l                                              # 305 files, 304 headers
grep -h '^@interface' "$H"/*.h | grep -v '(' | sed -E 's/^@interface +([A-Za-z0-9_]+).*/\1/' | sort -u | wc -l   # 315 classes
grep -h '^@protocol' "$H"/*.h | grep -v ';' | sort -u | wc -l           # 148 protocols
grep -h 'macos(26' "$H"/*.h | wc -l                           # 126 declarations
grep -h 'macos(27' "$H"/*.h | wc -l                           # 74 declarations
```

The glossary names 106 of the 463 classes and protocols (23%). A name in the
glossary is not coverage, and many headers are plumbing, so the figure only
bounds the footprint.

What the whole table says:

- **The kit is a control kit, not an app framework.** The looks of the controls
  are measured. What an app needs around them is missing: the lifecycle of the
  app and its windows, documents, a typed clipboard, a toolbar model, row
  content for tables, gestures, printing.
- **No ADR leaves any of these gaps out of scope on purpose.** The ADRs the
  rows cite explain the render stack (0033, 0034, 0047, 0056), the sidebar
  (0041), accessibility settings (0064), accents (0080) and icons (0081); only
  0081 bears on a gap (symbols). Every product choice is still open: see
  [decisions](#decisions).
- **Freya is the blocker in 8 of the top 20.** It has one DnD event (files),
  no overscroll, no paragraph options, a radius fixed before layout, a flex
  layout that only grows and physical left and right. The rest needs no Freya
  change.
- **The readers list 55 items new in macOS 26 and 44 new in macOS 27**, plus
  139 typed notification messages in the Swift overlay. Nearly all are absent.
  The ones that change the look are concentric corners, the glass views,
  `NSToolbarItem.Style` and layout regions.

## Top 20 gaps

The order is mine. The criterion: how many app designs the gap blocks, how
visible it is at first glance, and what the workaround costs the app author.
Size does not weigh. Each row links to its area.

## Decisions

Each decision is the user's. The options are mine; none is taken.

| # | Decision | Options | Blocks |
|---|---|---|---|

| D2 | Right-to-left | (a) mirror every view; (b) declare the kit left-to-right only | Gap 11 |
| D3 | Printing | (a) call `org.freedesktop.portal.Print` (the desktop draws the dialog, M); (b) a macOS-look panel over CUPS (L); (c) PDF export only | Gap 16 |
| D4 | Layout engine | (a) a constraint solver beside torin; (b) flex recipes plus `Grid`, `Spacer`, baseline | Gap 8 |
| D5 | Gesture layer | (a) SwiftUI-named `Gesture` over raw events; (b) raw events only; and whether to bind the unstable pointer-gestures | Gap 15 |
| D6 | Data model of lists | (a) `Identifiable` rows, selection by id; (b) keep index selection | Gap 3 |
| D7 | Clipboard and DnD payloads | (a) a `Transferable` trait over MIME types; (b) keep `Files` and `Text` | Gap 5 |
| D8 | Display options outside malaysia | (a) read the portal as a fallback; (b) malaysia only | Gap 14 |

| D10 | Window tabs | (a) tabs inside one toplevel; (b) tab groups the compositor owns | [Layout](#9-layout) |

| D13 | Symbols beyond the 124 | (a) more glyphs in the kit; (b) name lookup in the icon theme (revisits ADR 0081) | Gap 17 |

### 1. Windows, panels and the application

Rows (79): implemented 6, partial 27, absent 31, n/a 15, decision 0 (counted from the table; `decision needed` marks product choices, no ADR covers this area).
1. The kit has no app lifecycle: no quit/terminate hook, no close veto (`windowShouldClose`), no launch/active/hide hooks, no open-files path, no windowless (menu-bar-only) app. Freya's `Platform::exit()` and `open_url` are dropped by the runner (`runtime.rs`, `Platform::new` only logs).
2. Window state is thin: `WindowStatus` has 5 flags. xdg-shell states the runner never reads (tiled, suspended, constrained, bounds, wm_capabilities) are all parsed by sctk 0.20 already; screens, subtitle, document-edited, proxy icon, content layout guide, aspect ratio, Dock badge and attention are absent.
3. The portals and Wayland staging protocols give most of the rest cheaply: xdg-foreign (portal parent), xdg-toplevel-icon, xdg-system-bell, xdg-toplevel-drag, xdg-session-management, wp-alpha-modifier, plus Unity LauncherEntry for the badge.

### 3. Text system

52 rows (one per class or family): implemented 1, partial 25, absent 18, n/a 8, decision 0 (no ADR covers text). The macOS 26 and 27 table has 14 items (2 partial, 2 n/a, 10 absent). The three things that matter most:
1. The editor is a closed box: `TextEditor` has no read-only mode, no selection binding, no change/selection events, no Tab, one `SkParagraph` for the whole text (no viewport layout). Freya has the pieces (`freya-edit`, inline placeholders, `SelectableText`).
2. Rich text stops at bold/italic/link/family/size, and there is no paragraph model (indent, spacing, tabs, lists, tables, rulers): Freya wires only a subset of Skia's `TextStyle` and none of `ParagraphStyle`'s paragraph options.
3. Input and Linux conventions: text-input-v3 is bound for preedit/commit only (no surrounding text, no hints); text controls ignore the primary selection that the platform already implements.

### 7. Graphics: images, colors and drawing

Rows: implemented 9, partial 17, absent 24, decision 3, n/a 4 (57 rows). Headers read: NSImage, NSImageRep and its subclasses, NSColor, NSColorSpace, NSColorList, NSColorPanel, NSColorPicker/Picking, NSColorSampler, NSGradient, NSShadow, NSBezierPath, NSAffineTransform, NSGraphics, NSGraphicsContext, NSOpenGL*, NSMovie, NSAppearance (plus NSColorWell and NSImageView where they carry graphics API).
The matrix covers only symbols, the color well and the color panel. Nothing in it on semantic colors, color spaces, gradients, shadows, paths, transforms, bitmap reps or formats.
1. Color vocabulary is thin: three label tiers, one fill tier, no system colors (red to cyan), no app-defined adaptive color. `Role` is a closed enum (`crates/bk/src/styles.rs:211`).
2. Rendering is 8-bit sRGB end to end (`Rgba` sRGB f32; Freya `Color(u32)`; swapchain B8G8R8A8 + SRGB_NONLINEAR, `platform/vulkan.rs:377,421`): no Display P3, ICC or HDR `[26]`. `wp_color_management_v1` is staging (v3).
3. Drawing beyond controls means raw Skia: `CanvasContext` hands over the Skia canvas; the kit has no `Path` view, radial/angular gradient style, blend mode, color filter or offscreen render. Freya has most pieces; `bk` forwards few.

### 8. Animation, events and gestures

Rows (51): implemented 5, partial 25, absent 17, n/a 4, decision 0 (no ADR in `docs/decisions.md` touches animation, input, gestures or cursors). The existing matrix has no events, cursors or gestures section; this file is new ground.
1. The kit has no gesture layer (no recognizers, no long-press, no pinch/rotate/swipe) and the runner binds none of `pointer-gestures`, `pointer-constraints`, `relative-pointer`, `tablet-v2`; Freya 0.5.3 has raw Pointer/Touch/Wheel events and `EventsCombos` only.

The kit offers `Files` and `Text` only (`drag.rs`) and receives text and `text/uri-list` (`platform/clipboard.rs`). `decision needed`: a `Transferable` trait (SwiftUI name) over MIME types, or keep the two payloads.

## Discrepancies with the matrix

Where a reader's evidence contradicts [the matrix](swiftui-appkit-coverage.md). Each item names the matrix section. The matrix now carries the status changes for `WindowGroup`, `MenuBarExtra`, `.popover`, window tabs, `NSBackgroundExtensionView`, VoiceOver, `HSplitView`, `HStack`, `LazyVGrid`, `NSBrowser`, `NSRuleEditor` and the symbol count; the other items are open.

**Windows and application**

- §14 `WindowGroup`, `Window`, `Settings` | `NSWindow`, `NSWindowController` | `Application`, `SettingsWindow` | `implemented` P1. `Application::window` builds one scene; `WindowControls::open_window` returns no handle and no recipe uses it; no `openWindow(id:)`, `dismissWindow`, Window menu. Should be `partial`.
- §13 `MenuBarExtra` | `NSStatusItem` | `status_item` | `implemented`. The item is static (icon name, title, menu; pixmap empty; `Status` always `Active`) and exists only with a window. Should be `partial`.
- §13 `.popover` | `NSPopover` | `Popover` | `implemented` P1. `show` returns `()`: no close, behavior, edge or detach. Should be `partial`.
- §14 window tabs | `WindowTabs` | `implemented` P3. One toplevel, tabs not draggable, no tab group. Should be `partial`.
- §13 `.fileImporter`/`.fileExporter` P3. The portal call passes an empty parent window, no filters, no start folder; any document app needs these, so P2 at least.
- §18 lists only SwiftUI 27 APIs; the AppKit 26 and 27 items above are in no matrix row.

**Views and controls**

- §15 `backgroundExtensionEffect` / `NSBackgroundExtensionView`: matrix says `implemented`, P3. `docs/barrierkit/10-sidebar.md:317` says the kit stretches the first pixel column where Apple mirrors, only under a docked sidebar. It is `partial`.
- §3 `.menu` / `.segmented` / `.radioGroup` and §7 `ComboBox` are `measured`, but every item and label is `&'static str` (rg count in the Summary), which the rows do not say; the look is measured, the API for runtime lists is not.
- §11 says `prefersCompactControlSizeMetrics` "was not probed": the kit also has no switch for it, so every size row is the macOS 26 metric set only.

**Text**

- Section 7, `findNavigator` / `NSTextFinder` says `implemented`: the bar has a counter and previous/next only; no Replace, no options, no all-match highlight, so `partial`.
- Section 9, `NSFontPanel` says "no typeface collections or effects": `FontPicker` has three collections (All, Recently Used, Fixed Width; 06 chapter, Font panel). Missing are user collections, weights beyond four faces and effects.
- Section 7, `writingToolsBehavior, spelling, substitutions`: `partial: spelling only` agrees; add that Writing Tools is `n/a` (Apple service), not `missing`, and that `TextEditor` has no way to turn spelling off.
- Section 7, `NSTextView`/`TextEditor` row lists caret, selection, placeholder and find bar as unmeasured; the placeholder is drawn (text_editor.rs `empty`). Read-only mode, selection binding and events are absent and the matrix does not list them.

**Menus and toolbars**

- §13 `Menu`: says "item icons not measured". `macos-control-metrics.md` §Menus has the `menuui` probe (gap 8, icon column, 11 pt) and the bench `menu` scene has the `icons-` and `icons-marks-` sets (appkit.rs:831-855). "Not in Increase Contrast" is stale since f6a60a48 (kit takes the contrast inks); the bench scene still runs light and dark only (appkit.rs:866).
- §13 `.contextMenu` `implemented`: partial (secondary press only; no Menu key or long press).
- §13 `Commands`, `CommandMenu` `implemented`: partial (no `CommandGroupPlacement`, no standard menus; the export drops headers, icons, badges).
- §14 `.searchable` toolbar (`NSSearchToolbarItem`) `implemented`: partial (no begin/end interaction, fixed width, `collapsed` is app-driven).
- §14 `NSTrackingSeparatorToolbarItem` `missing`: partial (`Titlebar::with_sidebar` tracks the sidebar edge; inspector not).
- §14 `.expanded`: also missing in `infinity_window_style_v1.bar` (no value), so it needs the compositor.
- Docs conflict: `macos-menu-bar.md` §3 gives a menu panel corner of about 6 ("needs review"); `macos-control-metrics.md` §Menus gives about 14.

**Documents and drag and drop**

- §13 `.draggable`, `.dropDestination` says "drop only on the image well". File drops reach any element (`on_file_drop` and `on_global_file_hover`, `13-app.md` "Drag and drop"); `ImageWell` is one consumer. What fails is the rest: drag out has no image and Copy only, and text, URL or image drops from other apps are refused at `enter`.
- §1 `ShareLink` "copy, email and open only" is right, but Email is `mailto:?body=` (no subject, no attachments) while the Email portal v4 takes both; the Wallpaper portal (use as desktop picture) is unused. `05-controls.md` "freedesktop has no share portal" holds: the portal index has none.
- §13 `.fileImporter`, `.fileExporter` omits that `portal.rs` sets no filters, no start folder and passes `""` as the parent window.
- §14 `DocumentGroup`, `AlertScene` is `missing` at P3. `missing` holds; the close veto, the edited state and open-from-outside are needed by any editor, so P2 (the P3 items are Versions, iCloud, title menu).
- §1 `PasteButton` `missing` P3 holds, but it depends on P5 (no way to ask what is on the clipboard).

**Accessibility**

- §17 VoiceOver: "implemented: no audit per control", Evidence `platform/atspi.rs`. That file is 84 lines of adapter glue. Exposure is per control through `a11y_*`. The row should be `partial`: popups and tooltips publish no tree (`app.rs:223`), the window name is empty (`app.rs:387`), text has no ranges, only Focus and Click are served, and two tests assert nodes (`tests/kit/controls.rs:1198`, `:1279`).
- §17 focus ring, full keyboard access: one `partial` row. `ViewModifiers::focus_ring` always draws and is not `focusRingType`; Full Keyboard Access has no kit counterpart (the kit behaves as always on). Needs two rows.
- §17 Reduce Motion `implemented`, Increase Contrast, Reduce Transparency: correct inside Malaysia; outside it nothing reads the setting (no portal, no gsettings), which the matrix does not say. Add a row for the source.
- §17 Invert Colors, Differentiate Without Color: agree (`Resolved` has no `invert_colors`; `differentiate_without_color` read by `traffic_lights.rs:70` only).

**Graphics**

- §16 (`Image(systemName:)`): the matrix and `macos-icons.md` say 121 symbols; `Symbol` has 124 variants and the glossary table 124 rows. Any figure of 65 kit symbols is stale: it predates the 2026-11-20 work (`macos-icons.md` §3).
- §16 (`.symbolRenderingMode` row): it maps `TemplateRenderingMode` (original/template) to hierarchical, palette, multicolor. They are different axes: the kit has none of the three. Status should be `missing` for them.
- §18 lists only SwiftUI 27 APIs; four AppKit 27 items in this area (the typed notifications above) are in no list.
- Not a matrix item: `04-appearance-and-tokens.md:95` equates `Palette.destructive` with `NSColor.systemRed`; the token `danger` is `#cc2f35` (light) and `#ff6b6b` (dark), while `macos-control-metrics.md:181` measures systemRed `ff383c` and `ff4245`.

**Animation and events**

- Motion, `Animation` row: it names `Spring`, `ease_out`, `ease_in_out` as one family. Through `styles::Animation` only ease-out and `Spring` are reachable (`Ease` calls `spring(0.0)`, styles.rs:518); `ease_in_out` is used directly by a few views.
- Accessibility, Reduce Motion row (and `14-animations.md`: "Every kit animation then takes 0 ms"): `use_animated` does not check the preference; only Theme-resolved animations (`styles/theme.rs:33`) and `use_switch_progress` do; `progress.rs`, `backdrop.rs`, `glass_container.rs`, `views/split.rs` build `AnimNum` with no check in the file. Not run; a test per animation would settle it.
- The matrix has no section for events, cursors, gestures, key equivalents or the responder chain; all rows above are new to it.

**Layout**

- §12 `HSplitView`, `VSplitView` ↔ `NSSplitView` (`.thin`, `.thick`) → `SplitPanes` `implemented`: `.thick` and `.paneSplitter` are not drawn (`macos-control-metrics.md:344`), per-pane limits and keyboard on the divider are missing, so `partial`.
- §12 `HStack`, `VStack` ↔ `NSStackView` `implemented` (no gap): distribution, gravities, custom spacing, hiding priority and baseline alignment are absent, so `partial`.
- §12 `Form` `.columns` ↔ `NSGridView` `measured`: `FormStyle::columns` is a two-column label and control list (`views/form.rs:315`), not a grid; the `Grid` row (`missing`) stands.
- §12 `TabView` classic `measured`, no gap listed besides `Right`: inactive pages are unmounted, no disabled tab, no delegate hooks, no overflow (`tabs.rs:127`, `:257`).
- §18 `ContentMarginGuide`, `ReservedRegion` (27.1) P3: the AppKit twin `NSViewLayoutRegion` is macOS 26.0 and ties to the corner work; consider P2 together with concentric corners.

**Tables and collections**

- §12 `LazyVGrid`, `LazyHGrid` → `CollectionView` says `implemented`: it is `partial`. One vertical wrap of fixed 92 wide icon and name tiles, not virtualized, no horizontal axis, no `GridItem`, no sections.
- §12 `NSBrowser` → `Browser` says `implemented`: `partial`. No keyboard, single selection, fixed 200 wide columns, no titles or path API.
- §12 `NSPredicateEditor`, `NSRuleEditor` → `RuleEditor` says `implemented`: `partial`. Text, Number and Choice only; no Date or Boolean; no `nestingMode`; no predicate serialization.
- §12 `List` says `measured` with no caveat: it is `measured` for looks, but rows are `Vec<String>` (backlog C1 asks for free rows at P1; the section row does not say so).
- §12 `reorderable()` (macOS 27), swipe actions → drag in `NSTableView` at P3: reorder and drop on a row serve sidebars, playlists and Finder lists, so P2 is closer. `doubleAction` and type-select are in no row.
- The `.draggable`, `.dropDestination` row (it says "drop only on the image well"): `docs/barrierkit/13-app.md` "Drag and drop" says any element with `on_file_drop` receives dropped files; only files, never text or custom types.
- Backlog C7 "collection layouts, drop targets" P3: layouts beyond a grid are P3; a virtualized, sectioned grid is P1 for a photo app.

**Print, speech, sound**

- §13 `.fileImporter`, `.fileExporter` (`partial: the desktop's dialog`): true, and the matrix does not say the portal calls pass `""` as `parent_window` (`portal.rs`, `chooser.call(method, &("", title, options))`), so the dialogs are not attached to the window. Print would hit the same limit.
- §13 `NSPrintPanel`, `NSPageLayout` `missing` P3: agrees on status. The row covers two panels only; the work is the pipeline (PDF output, pagination, portal call), which has no row. P3 is low for any app with documents (see proposed rows).
- §13 `UNUserNotificationCenter` `implemented`: banners only; the sound setting (`AppNotifications.sound`) and the sound hints are not used. No row of the matrix covers sound, speech or the bell.

**Swift overlay**

- §13 `.draggable`, `.dropDestination`: "drop only on the image well". `13-app.md` «Drag and drop» says any element gets `on_file_drop` for files; only text and image drops are missing.
- §16 `.symbolEffect` → AppKit `NSSymbolEffect`: that class is not in this interface. The AppKit entry points are `NSImageView.addSymbolEffect`, `removeSymbolEffect`, `setSymbolImage(contentTransition:)` with `Symbols.SymbolEffect` (l.3425-3441).
